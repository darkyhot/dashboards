# Методология расчётов дэша `tb_health`

Документ описывает **все** расчёты, из которых собирается дэш «Здоровье ТБ», — чтобы
арифметику можно было перепроверить, не читая код.

Каждый раздел устроен одинаково: **что считаем → формула → где в коде → пример на числах**.

---

## 0. Как пользоваться документом

**Главная идея дэша.** Окончательная ЗП-ведомость существует только за ЗАКРЫТЫЙ месяц,
поэтому строить дэш «на июнь» в июле бесполезно: повлиять уже не на что. Дэш строится на
ТЕКУЩИЙ, незакрытый месяц, и вместо факта показывает **прогноз**:

```
прогноз(текущий месяц) = портфель(закрытый месяц) − ожидаемый отток + приход из пайплайна
```

Прогноз — **пассивный сценарий «если ничего не делать»**. Приход из пайплайна в него
уже заложен, а потенциал привлечения и удержание — нет: список организаций в дэше
показывает, чем прогноз можно улучшить.

**Числа в примерах.** Все примеры взяты из реального прогона на **синтетических** данных
открытого контура: ТБ ЮЗБ, прогнозный месяц июль 2026. На проме числа будут другими —
проверять надо формулы и совпадение промежуточных величин, а не сами значения.
Как воспроизвести пример — см. Приложение Б.

**Обозначения.** `{schema}` = `s_grnplm_ld_salesntwrk_pcap_sn_uzp` (витрины),
`{schema_t}` = `s_grnplm_ld_salesntwrk_pcap_sn_t_uzp` (пайплайн). Все SQL — в Приложении А.

## 1. Источники данных

| Таблица | Что берём |
|---|---|
| `uzp_dwh_metrics` | План и факт по метрикам на уровнях `tb` / `gosb`, по сегментам (`extended_dim_1`) и «все сегменты» (`=1`). Только `period_type='m'` |
| `uzp_dwh_company_holding_metric` | Витрина организаций: потенциал, отток, ФОТ, численность. Плюс 24 мес истории для модели оттока |
| `uzp_dwh_day_outflow` | Ежедневный отток текущего месяца: кто ещё не зачислился. Задаёт опорные даты |
| `{schema_t}.yva_pl_task_deal_code` | Пайплайн: помесячная раскладка плана привлечения |
| `uzp_dwh_sale_funnel_task` | Воронка: задачи, сделки, свободный текст отработки |
| `uzp_dim_mzp_reference_base` | Эталонная база закрепления: с какими парами (ГОСБ, организация) вообще можно работать |
| `uzp_dim_gosb`, `uzp_dim_company` | Справочники: ТБ→ГОСБ, сегмент и название организации |

**Две метрики:**
* `12400196` — количество уникальных получателей до организации (**главная**, все примеры по ней);
* `1000164` — общий ФОТ, в рублях (в отчёте делится на 1e6 и выводится как «млн ₽»).

**Грейн работы с клиентом — пара (ГОСБ, организация)**, а не просто организация: одна
компания обслуживается в нескольких ГОСБ, и в каждом своя история отработки.

**Маппинг ГОСБ.** Метрики и воронка лежат на `old_gosb_id`, реальный ГОСБ — это
`new_gosb_id`. Везде используется общий CTE `gmap`, сворачивающий `old → new`
(несколько старых ГОСБ могут отображаться в один новый). Для `uzp_dwh_day_outflow` этот
же джойн корректен при любой трактовке её `gosb_id`: множество `new_gosb_id` целиком
вложено в `old_gosb_id`, и для каждого такого значения `old → new` даёт само себя
(проверено на справочнике: конфликтов 0).

## 2. Опорные даты

**Что считаем.** Единые для всего дэша даты: какой месяц прогнозируем, по какое число
есть факт, какой месяц служит базой.

**Откуда.** `uzp_dwh_day_outflow` живёт ТОЛЬКО за текущий месяц (одно значение
`report_dt` и одно `act_dt`), поэтому именно она задаёт «сегодня».

| Величина | Формула | Смысл |
|---|---|---|
| `ref_cur` | `max(report_dt)` из `uzp_dwh_day_outflow` | прогнозный месяц (конец месяца) |
| `act_dt` | `max(act_dt)` при этом `report_dt` | по какое число есть факт зачислений |
| `ref_closed` | `ref_cur − 1 месяц` | закрытый месяц — база прогноза |
| `ref_funnel` | `= ref_cur` | конец окна воронки (задачи идут месяцем позже метрик) |
| `funnel_from` | первый день месяца `ref_cur − 2` | начало окна активностей (3 календарных месяца) |
| `fresh_from` | первый день месяца `ref_cur − 1` | сделки с этой даты считаются «свежими» |
| `hist_from` | конец месяца `ref_cur − (HIST_MONTHS + 1)` | нижняя граница истории, `HIST_MONTHS = 24` |
| `month_elapsed` | `день(act_dt) / день(ref_cur)` | какая доля месяца прошла |

Параметр `date` в тетрадке, если задан, означает **прогнозный** месяц. Если ежедневная
витрина пуста, дэш откатывается на прежнюю логику (`max(report_dt)` из витрины
организаций `+ 1 месяц`) и пишет об этом в прогрессе.

**Код:** `analyze._dates`. **SQL:** `REF_CUR`, фолбэк `REF_DATE`.

**Пример (ЮЗБ, синтетика):**
```
ref_cur       = 2026-07-31      act_dt      = 2026-07-26
ref_closed    = 2026-06-30      cur_month   = 7
funnel_from   = 2026-05-01      fresh_from  = 2026-06-01
hist_from     = 2024-06-30
month_elapsed = 26 / 31 = 0.8387
```

## 3. Прогноз портфеля

**Что считаем.** Прогноз получателей на текущий месяц и его сравнение с планом.

**Формула** (на любом уровне — ТБ, ГОСБ, (ГОСБ, сегмент)):

```
прогноз = портфель − ожидаемый_отток + сезонный_приход + пайплайн
```

* **портфель** — ФАКТ закрытого месяца из `uzp_dwh_metrics` (та же методика, что у плана,
  поэтому величины сопоставимы);
* **ожидаемый отток** и **сезонный приход** — из модели (разделы 4–5), считаются на грейне
  организаций и суммируются вверх;
* **пайплайн** — раздел 6;
* **план** — `plan_amt` из `uzp_dwh_metrics` за `ref_cur`.

Отток в отчёте разбит на две части, потому что это разные вещи по смыслу:
* **уже не зачислились** (`observed`) — факт, это уже случилось;
* **риск до конца месяца** (`risk`) — то, что ещё может не случиться, и на что можно повлиять.

`observed + risk = ожидаемый отток` по построению (`risk = out_exp − observed`).

**Потолок месяца** = прогноз при условии, что пайплайн отработают на 100%:
`портфель − отток + приток + пайплайн_заявленный`.

**Код:** `forecast.waterfall`, проверка сходимости — `analyze._check_waterfall`
(расхождение обязано быть нулевым).

**Пример (ЮЗБ, метрика получателей):**
```
портфель 06.2026            281 183.29
− ожидаемый отток             3 353.96   = уже не зачислились 3 083.00 + риск 270.96
+ сезонный приход                10.42
+ пайплайн                    4 947.63   (заявлено 9 518.00)
= прогноз 07.2026           282 787.37
  план 07.2026              312 014.98  → выполнение 90.6%, недобор 29 227.61
  потолок (пайплайн на 100%) 287 357.74
```
Проверка: `281 183.29 − 3 353.96 + 10.42 + 4 947.63 = 282 787.38` ✔

> **Важно:** `fact_amt` за текущий месяц в витрине метрик существует (частичная
> ведомость), но дэш его **не использует** — в этом и смысл прогноза.

## 4. Прогноз оттока по истории

**Что считаем.** Сколько получателей организация потеряет в прогнозном месяце, если
судить по её собственной истории за 24 месяца.

**Исходные признаки** (по паре ГОСБ+организация, из `uzp_dwh_company_holding_metric`):

| Признак | Что это |
|---|---|
| `base_fl` | получателей в закрытом месяце (`current_fl_qty` за `ref_closed`) |
| `out_1` | отток за закрытый месяц (`fl_outflow_qty` за `ref_closed`) |
| `out_2` | отток за предыдущий закрытый месяц |
| `seas_idx(m)` | средний `current_fl_qty` календарного месяца `m` ÷ средний за всю историю |
| `seas_ratio` | `seas_idx(месяц прогноза) / seas_idx(месяц базы)` |
| `yoy_out` | был ли отток в этом же календарном месяце год назад |
| `yoy_recovered` | восстановился ли клиент после того оттока |

**Почему `seas_ratio`, а не сам индекс.** Сезонность прогнозного месяца надо мерить
ОТНОСИТЕЛЬНО базового. Если июнь и июль одинаково «летние», сезонной дельты между ними
нет, хотя оба месяца отклоняются от годового среднего. Отношение это учитывает,
голый индекс — нет.

`seas_idx(m)` считается, только если календарный месяц наблюдался ≥ `MIN_SEASON_OBS = 2`
раз. Иначе сезонного сигнала нет, и модель сама деградирует до правила «два закрытых
месяца» — на короткой истории она не ломается, а упрощается.

`yoy_recovered` = год назад в этом месяце был отток **И** `current_fl_qty` в течение
1–3 месяцев после него вернулся к ≥ 95% доотточного уровня.

**Классы** (проверяются сверху вниз, первый сработавший выигрывает):

| Класс | Условие | `pred` |
|---|---|---|
| сезонный приход | `seas_ratio > 1.10` | `−base_fl × (seas_ratio − 1)` — отрицательный отток, то есть ПРИТОК |
| сезонный отток | `seas_ratio < 0.90` | `max(persist, base_fl × (1 − seas_ratio))`, и если `yoy_recovered` — ещё `× 0.4` |
| устойчивый отток | `out_1 > 0` и `out_2 > 0` | `persist = (out_1 + out_2) / 2` |
| разовый отток | `out_1 > 0` | `out_1 × 0.5` |
| стабильно | иначе | `0` |

где `persist = (out_1 + out_2)/2`, если оба > 0, иначе `0`.

Константы: `SEASON_UP = 1.10`, `SEASON_DOWN = 0.90`, `RECOVERED_K = 0.4`, `ONE_OFF_K = 0.5`.

**Ограничение сверху:** `pred ≤ base_fl` — нельзя потерять больше, чем есть.

**Смысл `RECOVERED_K`.** Если год назад клиент оттёк в этом же месяце и вернулся, это
**цикл, а не потеря**: сезонный бизнес, отпуска, вахта. Прогноз оттока по таким режется
в 2.5 раза, и в дэше рядом пишется «год назад тоже оттекал и восстановился к MM.YYYY».

**Код:** `forecast.outflow_model`. **SQL:** `OUTFLOW_HISTORY`.

**Примеры (ЮЗБ, синтетика):**

*Устойчивый отток* — ГОСБ 9052:
```
base_fl = 261, out_1 = 353, out_2 = 247, seas_ratio = 1.0355 (сезонности нет)
persist = (353 + 247) / 2 = 300
pred    = min(300, base_fl = 261) = 261
```

*Сезонный отток с восстановлением* — ГОСБ 8579:
```
base_fl = 235, out_1 = 104, out_2 = 0 → persist = 0
seas_ratio = 0.5573  (< 0.90 → сезонный отток)
pred = max(0, 235 × (1 − 0.5573)) = 235 × 0.4427 = 104.03
yoy_recovered = да → pred = 104.03 × 0.4 = 41.61
```

**Распределение классов на ЮЗБ:** разовый 202 · сезонный отток 192 · устойчивый 177 ·
стабильно 47 · сезонный приход 12 (всего 630 пар, история 24 мес).

## 5. Стыковка прогнозного и ежедневного оттока

**Что считаем.** Два источника говорят об оттоке одновременно, и они могут расходиться:
прогноз по истории (раздел 4) и ФАКТ текущего месяца из ежедневной витрины. Нужно одно число.

**Наблюдаемый отток.** Берётся как

```sql
min(outflow_unpaid_m_qty)  -- при act_dt = max(act_dt)
group by tb_id, gosb_id, org_inn
```

`min`, а не `sum`, потому что у организации в месяце обычно **две выплаты** (аванс и
основная), и отток надо считать ПО ИТОГУ обеих: если сотрудник получил хотя бы на одну
из дат, он не отток. Строка с авансом показывает больше неоплаченных, поэтому минимум
из двух строк и есть итоговый отток.

**Доля отыгранного риска** — какая часть месячного риска уже определилась:

```
settled = clip( max( month_elapsed, paid_mtd / fl_prev_m ), 0, 1 )
```

Два независимых измерителя, берётся больший:
* `month_elapsed` — доля прошедшего месяца, есть всегда;
* `paid_mtd / fl_prev_m` — доля получателей прошлого месяца, которые УЖЕ зачислились
  (`fact_fl_qty / fl_prev_m_qty` из витрины) — прямое измерение по организации.

Второй показатель — ключевой: если 97% людей уже получили деньги, риск месяца
практически отыгран, независимо от календаря.

**Итоговые величины:**

```
risk    = max(pred, 0) × (1 − settled)          — остаточный риск
out_exp = min( base_fl, max(наблюдаемый, risk) ) — ожидаемый отток
in_exp  = max(−pred, 0) × (1 − settled)          — сезонный ПРИТОК, отдельным слагаемым
```

Приток считается отдельно намеренно: внутри `max(...)` он был бы съеден нулём.

Организации, которых нет в ежедневной витрине (выплат в этом месяце не было), наблюдения
не имеют — у них `settled = 0`, то есть остаётся полный прогноз.

**Что даёт эта формула.** Факт — нижняя граница (что случилось, то случилось), прогноз —
верхняя оценка остаточного риска, и он «сгорает» по мере того, как месяц отыгрывается.

**Код:** `forecast.reconcile`. **SQL:** `DAY_OUTFLOW`.

**Примеры (ЮЗБ, синтетика):**

| Случай | pred | факт дня | settled | risk | `out_exp` |
|---|---|---|---|---|---|
| факт выше прогноза | 41.61 | 42 | 0.8387 | 6.71 | **42** |
| факт выше остаточного риска | 261.00 | 51 | 0.8387 | 42.10 | **51** |
| **прогноз не оправдался** | 254.00 | 2 | 0.9933 | 1.70 | **2** |

Последняя строка — ровно кейс из бизнес-постановки: модель ждала 254 человека оттока,
а по факту не зачислились только 2, потому что 99% портфеля уже получили выплаты.
Прогноз «сгорел», в расчёт пошёл факт.

Обратный случай тоже работает: если модель ждала 3, а не зачислилось 100, берётся 100.

## 6. Пайплайн и коэффициент реализуемости

**Что считаем.** Сколько новых получателей придёт в прогнозном месяце по сделкам,
которые сотрудники уже завели.

**Почему нужна отдельная таблица.** В `uzp_dwh_sale_funnel_task` поле
`plan_staff_deal_qty` — это план на **все три месяца** жизни сделки. Помесячной разбивки
там нет; она есть только в `{schema_t}.yva_pl_task_deal_code`
(`pl_month_num`, `pl_plan_np_amt`). Берём строки с `pl_month_num = месяц(ref_cur)`.

**Ключ связи:** `coalesce(deal_code, task_code) = pl_task_deal_code` — в пайплайн входят
и офферы без заведённой сделки.

**Обязательная дедупликация.** Один `deal_code` встречается в НЕСКОЛЬКИХ строках воронки
(по сделке заводят несколько задач). Прямой джойн задвоил бы план, поэтому в запросе
сначала CTE `codes` сворачивает воронку до уникального кода, и только потом идёт join.

**Окно.** Те же 3 месяца, что у активностей (`funnel_from … ref_funnel`): сделка живёт
3 месяца, поэтому запланировать текущий месяц могли только сделки этого окна.

**Коэффициент реализуемости.** Заявка сотрудника — оптимистичный план, поэтому прогноз
берёт её с поправкой на историю:

```
conv(ГОСБ) = sum(fact_staff_deal_qty) / sum(plan_staff_deal_qty)
             по сделкам, созданным РАНЬШЕ fresh_from
conv = clip(conv, 0.2, 1.0)          -- CONV_MIN / CONV_MAX
пайплайн = pl_plan_np_amt × conv
```

Свежие сделки (созданные в двух последних месяцах окна) в расчёт коэффициента не
берутся: они ещё не успели реализоваться и занизили бы его. Если по ГОСБ истории нет,
используется коэффициент ТБ; если нет и его — `1.0`.

В дэше показываются **оба** числа: с поправкой (базовый прогноз) и заявленное
(«если пайплайн отработают на 100%» — потолок месяца).

**Код:** `forecast.conversion`, `forecast.pipeline_np`. **SQL:** `PIPELINE`, `DEAL_CONVERSION`.

**Пример (ЮЗБ, синтетика):**
```
по «старым» сделкам:  план 5 624 → факт 2 813
conv = 2 813 / 5 624 = 0.5002   (в границах [0.2, 1.0])
пайплайн: заявлено 9 518 → в прогнозе 9 518 × 0.5002 = 4 947.63
недоработка пайплайна = 9 518 − 4 947.63 = 4 570.37 чел — это и есть потолок месяца
```

## 7. Матрица ГОСБ × сегмент

**Что считаем.** Прогноз выполнения плана в разрезе (ГОСБ, сегмент) — это грейн, на
котором дальше идёт отбор организаций.

**Формула ячейки:**
```
прогноз(ГОСБ, сегмент) = факт закрытого месяца(ГОСБ, сегмент)   [из uzp_dwh_metrics]
                       − Σ out_exp + Σ in_exp + Σ пайплайн       [по организациям]
недобор = план(ГОСБ, сегмент) − прогноз
```

**Сегмент организации** определяется по приоритету: `segment_name` из ежедневной витрины
(короткое имя, основной источник) → сегмент из воронки → справочник `uzp_dim_company`
(большое имя приводится к короткому) → «—».

**Разнос неатрибутированного.** Дельта организаций, чей сегмент неизвестен или
отсутствует в плановой матрице этого ГОСБ, разносится по сегментам ГОСБ **пропорционально
базовому факту** — иначе сумма ячеек не сойдётся с итогом по ГОСБ. Объём разнесённого
печатается в прогресс.

**Строка «прочие»** в карточке ГОСБ закрывает разницу между итогом ГОСБ и суммой
показанных сегментов; выводится, только если остаток превышает `REST_MIN_SHARE = 0.005`
(0.5%) плана ГОСБ. После перехода на показ ВСЕХ сегментов она остаётся в основном для
известного расхождения уровней `tb`/`gosb` (раздел 12).

**Код:** `forecast.build_matrix`, `forecast.build_totals`. **SQL:** `GOSB_SEG`, `GOSB_TOTALS`.

**Пример — Калмыцкое ГОСБ № 8579 × ММБ (ЮЗБ, синтетика):**
```
портфель 06.2026     15 774.56
− отток                 170.39
+ приток                  0.00
+ пайплайн              167.43
= прогноз            15 771.59
  план               20 115.38  → выполнение 78%, недобор 4 343.79
```

## 8. Разрыв и отбор организаций под план

**Что считаем.** Не «весь потенциал ТБ», а минимальный набор организаций, закрывающий
разрыв КАЖДОГО западающего сегмента.

**Западающий сегмент:** `недобор ≥ MIN_SEG_GAP = 1` человек (порог отсекает шум
округления; это тот же признак, что красит ячейку тепловой карты в красный).

**Алгоритм для цели `k`** (`_mark_needed`), отдельно по каждому ГОСБ:

* **Фаза 1 — свой сегмент.** Для каждого западающего сегмента (по убыванию разрыва)
  цель `target = недобор × k`. Берём организации ЭТОГО сегмента в ЭТОМ ГОСБ по убыванию
  эффекта, пока накопленный эффект не достигнет `target`. Недобранное `lack` копится.
* **Фаза 2 — добор.** Если своих не хватило, остаток закрываем организациями ДРУГИХ
  сегментов того же ГОСБ, помечая строки как доборные.

**Цели.** `PLAN_TARGETS = (1.0, 1.2, 1.5)` — «выполнить план / +20% / +50%». Алгоритм
прогоняется от большей цели к меньшей, и каждой строке остаётся **минимальная** цель, при
которой она нужна (`need_k`). В HTML переключатель «Цель» просто сравнивает `need_k` с
коэффициентом, поэтому фильтр работает поверх остальных и ничего не пересчитывает.
`need_k = 0` — организация не нужна ни при какой цели, видна только в режиме «все».

**Из отбора исключены** организации вне эталонной базы `uzp_dim_mzp_reference_base`
(фильтр `EXISTS` без условий на `actual_dt`, так как срезов несколько): работать с ними
нельзя, сколько бы потенциала у них ни было.

**Код:** `analyze._mark_needed`, `analyze._select`, `analyze._plan_summary`.

**Пример — ММБ Калмыцкого ГОСБ (цель 1.0):**
```
недобор сегмента           4 343.79 чел
отобрано организаций              14  (это ВСЕ доступные в сегменте)
суммарный эффект                +765 чел
покрытие = 765 / 4 343.79 =    17.6%  → «в сегменте хватает на 18%, добор из других»
```

**Итог по ЮЗБ:** под план нужно 243 организации на +25 532 чел и ~1 612 млн ₽ ФОТ
(привлечение 21 306, возврат 3 812, добор из других сегментов — 106 организаций);
весь доступный потенциал западающих сегментов покрывает разрыв на 69%.

## 9. Три рычага и защита от двойного счёта

**Что считаем.** По каждой паре (ГОСБ, организация) — какой рычаг даёт больший эффект.

| Рычаг | Эффект | Смысл |
|---|---|---|
| **Привлечь** | `max(0, потенциал − пайплайн)` | новые получатели |
| **Вернуть** | `fl_outflow_qty` закрытого месяца | ушедшие в прошлом месяце |
| **Удержать** | `out_exp`, если месяц ещё не кончился | оттекают ПРЯМО СЕЙЧАС |

Рычаг = тот, у кого эффект максимален; он же задаёт `impact_fl` и эффект по ФОТ.

**Защита от двойного счёта.** Приход из пайплайна УЖЕ заложен в прогноз, поэтому эффект
привлечения уменьшается на него. Иначе одна и та же сделка была бы посчитана дважды:
один раз в прогнозе, второй — в списке «что добавит план».

**Почему удержание считается целиком, а не «остаточным риском».** Люди, не зачислившиеся
к отчётной дате, и есть предмет работы — в самой витрине под это заведён отдельный
признак `is_d_outflow_task` («выставить задачу на ежедневный отток»). Если месяц уже
закончился (`days_left = 0`), рычаг выключается: удерживать нечего, остаётся «Вернуть» в
следующем месяце.

**Рычаги не пересекаются:** «Вернуть» — про отток ЗАКРЫТОГО месяца, «Удержать» — про
ТЕКУЩИЙ, это разные популяции.

В классификации удержание идёт **первым**: если получатели не зачисляются прямо сейчас,
а месяц ещё открыт, это срочнее и свежей сделки, и разбора старых задач.

**Код:** `analyze._candidates`, `analyze._classify`.

**Пример (ЮЗБ):** в списке к работе 342 пары — Привлечь 228 · Удержать 68 · Вернуть 46.

## 10. Аудит отработки (правила и LLM)

**Что считаем.** По каждой паре — есть ли ПРЯМО СЕЙЧАС действие, которое зависит от банка
и может дать получателей.

**Пул на аудит:** ВСЕ организации западающих сегментов их ГОСБ + доборные из других
сегментов (под цель 1.5), с порогом по эффекту `llm_min_impact` (по умолчанию 1 чел) и
жёстким потолком вызовов `llm_max_calls` (80). Хвост, не влезший в бюджет, разрешается
правилами.

**Порядок разрешения** (первое сработавшее выигрывает):

1. **Чек-лист** — структурная причина оттока из анкеты. Если она означает «влиять нечем»
   (ликвидация, отпуска/сезонность, сокращение штата), это короткое замыкание: поле формы
   надёжнее догадки по тексту.
2. **Названный срок в будущем** — если в тексте есть срок позже текущего месяца и
   просрочки нет, вердикт `in_progress` («Проконтролировать в MM.YYYY»). В LLM не идёт.
3. **Ключевые слова** (regex + анти-отрицание) — но НЕ применяются, если у пары ≥ 2
   авторов (противоречия между сотрудниками может оценить только модель) или если правило
   помечено `needs_llm`.
4. **LLM** — получает ФАКТЫ витрины и хронологию заметок.
5. **Фолбэк на правила** — для того, что не влезло в бюджет или на что модель не ответила.

**Что уходит в LLM.** По паре: числовые ФАКТЫ (в том числе ожидаемый отток текущего
месяца с классом и пояснением, и план пайплайна на месяц) + хронология активностей с
ОБЕЗЛИЧЕННЫМ автором (`Сотрудник-01` по табельному). Названия ГОСБ и компаний **не
отправляются** — только числовые id; в нарративе используются псевдонимы, реальные имена
подставляются обратно после ответа.

**Ответ модели:** `verdict` (`work` / `no_point` / `in_progress`), `can_influence`,
`quality`, `contradiction`, `outflow_worked`, `attract_real`, `reason`, `action`.

**Постобработка** (`_finalize`) гасит метки там, где они бессмысленны: «формально
закрыто» / «не отработана» — только если задачи вообще закрыты; «отток не отработан» —
только при реальном оттоке и когда банк мог на него повлиять; `can_influence = нет`
переводит вердикт в `no_point` с действием «Мониторинг, действий не требуется».

**Вердикты `no_point` и `in_progress` убирают пару из списка к работе** — список
отвечает на вопрос «что мы РЕАЛЬНО можем сделать сейчас», а покрытие плана после этого
честно падает.

**Код:** `analyze._resolve`, `analyze._deterministic`, `analyze._finalize`,
`text_rules.py`, `prompts.py`. **SQL:** `FUNNEL_AGG`, `FUNNEL_TEXT`.

## 11. Детализация прогноза по ГОСБ

**Что считаем.** Разбор «почему прогноз такой» — то, что открывается по клику на карточку.

**Почему не «топ-5 клиентов».** Именами число объяснить нельзя. На Калмыцком ГОСБ отток
552 чел размазан по 67 организациям: **топ-5 объясняют лишь 32%**, топ-10 — 55%, и только
топ-20 доходит до 80%; крупнейший клиент — 7.6%. Поэтому детализация идёт от структуры к
именам.

**Два разбора оттока:**
* **по причине** — классы модели (раздел 4);
* **по зоне влияния** — можно работать (пара в списке к отработке) / влиять нечем
  (вердикт `no_point`) / вне эталонной базы (работать нельзя).

Второй разбор и есть ответ на «ну посмотрел я и что?»: он показывает, какая часть оттока
вообще ваша.

**Материальность имён.** Организация называется, только если её вклад
≥ `DETAIL_MIN_SHARE = 0.05` (5%) блока **и** ≥ `DETAIL_MIN_FL = 3` чел, максимум
`DETAIL_MAX_ROWS = 8` строк. Остальное сворачивается в одну честную строку
«ещё N орг. на M чел». Показанные + хвост = итог блока (проверяется).

**Код:** `analyze._gosb_detail`, `analyze._material`, `analyze._bucket`.
**SQL:** `ORG_DETAIL`.

**Пример — Калмыцкое ГОСБ № 8579, отток 552 чел:**

| По причине | чел | орг | | По зоне влияния | чел | орг |
|---|---|---|---|---|---|---|
| устойчивый отток | 297 | 21 | | влиять нечем | 310 | 24 |
| сезонный отток | 199 | 20 | | **можно работать** | **179** | **28** |
| разовый отток | 54 | 17 | | вне эталонной базы | 64 | 8 |
| сезонный приход | 2 | 1 | | | | |
| стабильно | 1 | 1 | | | | |

Названо 8 организаций, хвост — 52 организации на 287 чел.

**Тренд портфеля год к году** — отдельный блок (`fl_y_1_diff_qty` за закрытый месяц):
это структурный тренд, а не прогноз месяца, поэтому он вынесен из водопада.

## 12. Известные расхождения и ограничения

1. **Сумма ячеек матрицы ≠ итог по ТБ.** Уровни `tb` и `gosb` в `uzp_dwh_metrics` — разные
   строки и совпадать не обязаны. Кроме того, в справочнике есть `old_gosb_id`,
   числящиеся сразу под ДВУМЯ `tb_id` (в текущем справочнике таких два: 1002 и 1009);
   `gmap` относит такой ГОСБ к меньшему `tb_id`, и его метрики попадают в строку уровня
   `tb`, но не в строки уровня `gosb`. Дэш **печатает величину расхождения в прогресс**,
   а не прячет его. Собственная арифметика прогноза (водопад) при этом обязана сходиться
   в ноль и проверяется отдельно.
2. **Ранг ТБ считается по ЗАКРЫТОМУ месяцу** и так и подписан: в текущем месяце факт
   витрины частичный, ранжировать по нему нельзя, а прогноз по всем 12 ТБ здесь не считается.
3. **`fact_amt` текущего месяца не используется** — частичная ведомость занижена по
   определению.
4. **Организации вне эталонной базы входят в прогноз, но не в список к работе.** Они
   реально влияют на портфель, но работать с ними нельзя. На ЮЗБ это ~12% ожидаемого
   оттока — в детализации по ГОСБ они выделены отдельной строкой.
5. **Сезонность требует ≥ 2 наблюдений календарного месяца.** На истории короче ~13
   месяцев год-к-году не считается, и модель работает только на двух закрытых месяцах;
   фактическая глубина истории печатается в прогресс.
6. **`pl_month_num` — номер месяца без года.** Неоднозначность снимается окном воронки:
   запланировать текущий месяц могли только сделки последних 3 месяцев.

## Приложение А. SQL

Все запросы лежат в [uzp_dash/dashboards/tb_health/queries.py](uzp_dash/dashboards/tb_health/queries.py).
`{schema}` / `{schema_t}` подставляются автоматически, `:name` — параметры.

Общий CTE, используемый почти везде (`old_gosb_id → new_gosb_id`):

```sql
gmap AS (
  SELECT old_gosb_id, min(tb_id) AS tb_id, min(new_gosb_id) AS new_gosb_id,
         min(new_gosb_name) AS gosb_name
  FROM {schema}.uzp_dim_gosb GROUP BY old_gosb_id
)
```

### Опорные даты — `REF_CUR`
```sql
SELECT r.ref_cur,
       (SELECT max(d.act_dt) FROM {schema}.uzp_dwh_day_outflow d
        WHERE d.report_dt = r.ref_cur) AS act_dt
FROM (SELECT max(report_dt) AS ref_cur FROM {schema}.uzp_dwh_day_outflow) r
WHERE r.ref_cur IS NOT NULL
```

### Ежедневный отток — `DAY_OUTFLOW`
Параметры: `:tb_id`, `:ref_cur`, `:act_dt`.
```sql
WITH gmap AS (...)
SELECT g.new_gosb_id, d.org_inn AS inn,
       max(d.segment_name)                 AS seg_day,
       min(d.outflow_unpaid_m_qty)         AS out_observed,
       max(d.fact_fl_qty)                  AS paid_mtd,
       max(d.fl_prev_m_qty)                AS fl_prev_m,
       max(d.m_avg_salary_amt)             AS avg_salary_m,
       count(DISTINCT d.payment_order_num) AS n_payments
FROM {schema}.uzp_dwh_day_outflow d
LEFT JOIN gmap g ON g.old_gosb_id = d.gosb_id
WHERE d.report_dt = :ref_cur AND d.act_dt = :act_dt AND d.tb_id = :tb_id
GROUP BY g.new_gosb_id, d.org_inn
```

### История для модели оттока — `OUTFLOW_HISTORY`
Параметры: `:tb_id`, `:hist_from`, `:ref_closed`.
```sql
WITH gmap AS (...)
SELECT g.new_gosb_id, c.org_id AS inn, c.report_dt,
       COALESCE(c.fl_outflow_qty, 0) AS fl_outflow_qty,
       COALESCE(c.current_fl_qty, 0) AS current_fl_qty
FROM {schema}.uzp_dwh_company_holding_metric c
JOIN gmap g ON g.old_gosb_id = c.level_id
WHERE g.tb_id = :tb_id AND c.org_type = 'inn'
  AND c.report_dt >  CAST(:hist_from  AS date)
  AND c.report_dt <= CAST(:ref_closed AS date)
```

### Пайплайн — `PIPELINE`
Параметры: `:tb_id`, `:funnel_from`, `:ref_funnel`, `:cur_month`.
```sql
WITH gmap AS (...),
codes AS (                          -- дедупликация: один deal_code = одна строка
  SELECT COALESCE(f.deal_code, f.task_code) AS code, f.inn,
         min(g.new_gosb_id)                      AS new_gosb_id,
         min(f.segment_name)                     AS seg_funnel,
         sum(COALESCE(f.fact_staff_deal_qty, 0)) AS fact_deal
  FROM {schema}.uzp_dwh_sale_funnel_task f
  LEFT JOIN gmap g ON g.old_gosb_id = f.gosb_id
  WHERE f.tb_id = :tb_id
    AND f.task_create_dt >= CAST(:funnel_from AS date)
    AND f.task_create_dt <= CAST(:ref_funnel  AS date)
    AND COALESCE(f.deal_code, f.task_code) IS NOT NULL
  GROUP BY 1, 2
)
SELECT c.new_gosb_id, c.inn, min(c.seg_funnel) AS seg_funnel,
       sum(COALESCE(p.pl_plan_np_amt, 0))  AS pipe_np_raw,
       sum(COALESCE(p.pl_plan_fot_amt, 0)) AS pipe_fot_raw,
       sum(c.fact_deal) AS fact_deal, count(*) AS n_deals
FROM codes c
JOIN {schema_t}.yva_pl_task_deal_code p ON p.pl_task_deal_code = c.code
WHERE p.pl_month_num = :cur_month
GROUP BY c.new_gosb_id, c.inn
```

### Коэффициент реализуемости — `DEAL_CONVERSION`
Параметры: `:tb_id`, `:fresh_from`. Строка с `new_gosb_id IS NULL` — итог по ТБ (фолбэк).
```sql
WITH gmap AS (...),
base AS (
  SELECT g.new_gosb_id,
         COALESCE(f.plan_staff_deal_qty, 0) AS plan_q,
         COALESCE(f.fact_staff_deal_qty, 0) AS fact_q
  FROM {schema}.uzp_dwh_sale_funnel_task f
  LEFT JOIN gmap g ON g.old_gosb_id = f.gosb_id
  WHERE f.tb_id = :tb_id
    AND COALESCE(f.plan_staff_deal_qty, 0) > 0
    AND f.deal_create_dttm IS NOT NULL
    AND f.deal_create_dttm < CAST(:fresh_from AS date)
)
SELECT new_gosb_id, sum(plan_q) AS plan_q, sum(fact_q) AS fact_q FROM base GROUP BY 1
UNION ALL
SELECT NULL, sum(plan_q), sum(fact_q) FROM base
```

### План и факт метрик
* `TB_VERDICT` — обе метрики уровня `tb` за `:ref` + ранг ТБ (window-функция).
  Вызывается ДВАЖДЫ: за `ref_closed` (портфель-база и ранг) и за `ref_cur` (план).
* `GOSB_SEG` — (ГОСБ, сегмент), `extended_dim_1 <> 1`. Тоже дважды.
* `GOSB_TOTALS` — итог по ГОСБ, `COALESCE(extended_dim_1, 1) = 1`.

### Организации
* `ORGS` — витрина организаций за `:ref_closed` с фильтром эталонной базы
  (`EXISTS`, без условий на `actual_dt`).
* `ORG_DETAIL` — то же БЕЗ фильтра эталонной базы, плюс `fl_y_1_diff_qty` (тренд год к
  году) и флаг `in_ref`: имена нужны и для организаций вне базы, иначе часть оттока
  окажется безымянной.
* `FUNNEL_AGG` / `FUNNEL_TEXT` / `ACTIVITY_*` — агрегаты и свободный текст воронки.

## Приложение Б. Как воспроизвести пример (синтетика)

Числа в примерах получены в открытом контуре на сгенерированных данных.

```bash
docker compose up -d                      # Postgres на порту 55433
python -c "import synth; print(synth.build('postgresql+psycopg2://uzp:uzp@localhost:55433/uzp'))"
```
затем в `run.ipynb` — контур `open`, `tb = "ЮЗБ"`, `date = "2026-07-31"`.

**Как устроена синтетика** (`synth/generate.py`), чтобы числа были объяснимы:

* Последний ЗАКРЫТЫЙ месяц — `2026-06-30`, прогнозный — `2026-07-31`, `act_dt` = `26.07`.
* `uzp_dwh_company_holding_metric` содержит 24 месяца. История рисуется **назад** от
  текущих значений, поэтому закрытый месяц бит-в-бит совпадает с исходной витриной
  (проверено: расхождение 0 по всем полям).
* Каждой организации назначен архетип истории, чтобы встретился КАЖДЫЙ класс модели:
  ровный · устойчиво оттекающий · разовый отток · сезонный спад с восстановлением ·
  сезонный приход. Сезонное окно — `(7, 8, 9)`, то есть начинается с прогнозного месяца:
  иначе база и прогноз лежали бы в одной фазе сезона и сезонной дельты не возникло бы.
* Ежедневная витрина намеренно воспроизводит **оба** кейса стыковки: организации, у
  которых прогноз не оправдался (факт ≈ 0), и организации с крупным фактом, которого
  модель не ждала. У ~30% организаций прошла только первая выплата месяца.
* План текущего месяца выводится **из прогноза**: `plan = прогноз / целевое выполнение`,
  где целевое выполнение — тот же сценарий, что в закрытом месяце (ЮЗБ проваливает план,
  остальные 11 ТБ выполняют). Поэтому выполнение по ЮЗБ и получается около 90%.
* `fact_amt` текущего месяца записывается как 62% прогноза — «частичная ведомость».
  Дэш её не использует; она нужна, чтобы было видно, если кто-то возьмёт её по ошибке.

**Что проверять в первую очередь на промышленных данных:**
1. водопад сходится (`портфель − отток + приток + пайплайн = прогноз`);
2. глубина истории ≥ 13 месяцев (иначе сезонность отключается — видно в прогрессе);
3. коэффициент реализуемости не упёрся в границу `0.2` или `1.0`;
4. доля оттока вне эталонной базы (если велика — список к работе объясняет мало);
5. расхождение суммы ячеек матрицы с итогом ТБ (печатается в прогресс).
