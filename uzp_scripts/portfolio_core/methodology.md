# Порог сторожа и его диагностика

Для каждого потока и уровня (`org`, `atom`) `watch.scan_rows` оценивает факт O,
ожидание E и шум s. Ожидание берётся по ставке похожей группы в других ТБ с поправкой
на собственную прошлую ставку. Шум учитывает ожидаемый объём, разброс класса размера
и собственный устойчивый разброс ряда. Реализация — `ptf/watch.py`.

## Текущее правило отбора

Для прошлых месяцев h сначала отбираются отклонения с
`|O_h − E_h| ≥ max(100, 0,001 × база_h)`. В общий список потока попадают
`|O_h − E_h| / s_h` всех таких строк уровня. Список сортируется по убыванию.

При бюджете 0,5 и H исторических месяцах индекс порога равен `floor(0,5 × H)`
с нуля. Например, при H=12 используется седьмое значение. К нему прибавляется
малое положительное число, чтобы равенство не создавало лишнего срабатывания.

Второй порог — нормальная поправка на число проверок:
`NormalDist.inv_cdf(1 − 0,5 / (2 × число_строк × 6))`.
Итоговый z — максимум двух порогов. Карточка проходит первичный отбор, если
`L = |O − E| − z × s ≥ max(100, 0,001 × база)`.

Исторический порог общий для всех строк потока данного уровня. Он не является
оценкой собственного шума конкретной организации. Настоящее большое событие или
ошибка ожидания в одной исторической строке может поднять его остальным. Нельзя
считать весь исторический хвост заведомо чистым фоном.

## Что показывает раздел «пороги»

По сохранённым пропускам выбирается месяц с самым большим порогом нужного потока.
Один вызов `scan_rows(..., details=True)` разбирает соответствующий уровень уже
загруженной панели. Сборки, запросов к БД и закладок событий нет.

На странице источников показаны первые три строки исторического хвоста и строка
на позиции, используемой для исторического порога. Ранг начинается с единицы.
Признак «задаёт порог» установлен, если исторический порог определяет итоговый z.
Ряды обозначены условными кодами, без исходных номеров организаций.

Подробный режим добавляет сведения об источниках, не меняя E, s, z или отбор.
Это проверяется регрессионным тестом. Смена страницы использует кэш.

В разборе реорганизации у принимающей стороны проверяется поток `in_other`,
у отдающей — `out_other`. Просмотр работает как с результатом в памяти,
так и со структурой ранее сохранённого JSON.

## Ограничения

В старых отчётах есть итоговый порог и параметры пропущенного события, но нет строк
истории, сформировавших этот порог. Их нельзя восстановить только из такого JSON.
Для их разбора нужна исходная панель того же поколения в памяти Jupyter.

Числа в таблицах округлены для чтения. L вычисляется по неокруглённым величинам;
по округлённым O, E, s и z он может воспроизводиться с небольшим расхождением.
Нормальная поправка сама по себе не гарантирует уровень ложных тревог на реальных
данных. Текущий дефект завышенного общего исторического порога пока не исправлен.

Кейс C01 выявил отдельный вопрос нормализации: m_out_temp включает временные
уходы разных типов. Возврат второй работы может относиться к in_other.
Полный вычет предыдущего m_out_temp из in_outside создавал отрицательный поток.
Исправление от 05.11: m_in_temp_outside считает приход именно извне той же тройки
с портфелем в M−2 и пропуском в M−1; сторож вычитает эту часть из текущего прихода.
m_out_temp_left — пересечение временного ухода с уходом именно из банка;
только оно используется для календарной коррекции ухода. Эти меры сохраняются
при новой сборке. Суммы по общим маркерам не заменяют точные пересечения.
При неизвестной мере скорректированный поток остаётся неизвестным, противоречивые
счётчики вызывают ошибку. Старый отчёт можно воспроизвести отдельно для диагностики,
со старой коррекцией и явной подписью; это не применение нового сторожа.

## Первый бизнес-разбор

`ptf/business.py` суммирует только атомы. Изменение троек между соседними остатками
сопоставляется с шестью исходными потоками; невязка и отличие месячной базы от
предыдущего остатка показываются явно. Проверяется и тождество каждого атома:
встречные ошибки не могут погасить друг друга. Допуск — 0,01, как при сборке.
Для долевых ФЛ банка: `ΔФЛ = m_fl_in − m_fl_out + m_fl_conc + невязка`.

Месяц выбирается по максимуму `|Δбанка|`, `Σ|Δатомов|/2`, `Σ|Δкрупных организаций|/2`.
Это ранжирование изменений остатков, а не статистическая значимость или число
уникальных людей. Срезы используют разность остатков; различие с месячной базой
выделено отдельно. Например, в проверяемом сценарии второй работы: тройки −1,
долевые ФЛ 0, внутренний отток троек 1. Внешний уход людей из этого не следует.
Пустые меры не заменяются нулями; неполный расчёт не получает статус «проверено».
Экран показывает крупнейшие вклады и остаток, HTML сохраняет все срезы.
Календарная причина и точная доля её влияния этим расчётом не доказываются.
