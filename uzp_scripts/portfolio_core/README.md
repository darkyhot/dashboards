# portfolio_core — единая подложка портфеля ФЛ

Раз в месяц читает ведомости за последние 36 месяцев, размечает, что случилось с
каждым получателем ЗП, и хранит результат сводкой «месяц × id орг × ГОСБ». Любой
вопрос про портфель отвечается запросом к сводке — без нового чтения ведомостей.

Что и как считается — [DESIGN.md](DESIGN.md).

## Что появляется в БД

В `s_grnplm_ld_salesntwrk_pcap_sn_t_uzp`:

| Таблица | Что это |
|---|---|
| `yva_ptf_month_org` | сводка: 90 столбцов, строка = месяц × id орг × ГОСБ. Пересоздаётся каждым прогоном |
| `yva_ptf_flow_pairs` | потоки людей «организация → организация» к прошлому месяцу. Пересоздаётся |
| `yva_ptf_journal` | журнал: итоги и точное число людей по банку, ТБ, сегментам — по каждому прогону. Копится |
| `yva_ptf_vintage` | поколения: ключевые меры на дату прогона по срезам и крупным организациям. Копится |

Старая таблица `yva_ptf_runs` (журнал этапа 1) больше не пишется — её можно удалить.

Людей в постоянных таблицах нет: всё, где есть `epk_id`, живёт только во временных
таблицах прогона. Сводка и потоки подменяются одной транзакцией, **только если сошлись
все самопроверки**; иначе старые остаются, а новые лежат в `_new` для разбора.

## Как запускать

Тетрадка `portfolio_core.ipynb`, по ячейкам сверху вниз:

1. Самопроверки — секунды. Не прошли — дальше нельзя.
2. Параметры и запуск. `REPORT_MONTH` задаётся явно — последний закрытый месяц.
3. Итоги: проверки, портфель по месяцам, пересчёт прошлого, самые долгие шаги.
4. Примеры запросов к сводке.

Начало окна считается само: последние `N_MONTHS`, но не раньше 2023-11.
Лимит на оператор — `SQL_TIMEOUT_MIN = 60`. Если оператор всё равно упал по
таймауту на шагах «Метки движений» или «Остатки» — `EPK_CHUNKS = 4` (результат тот
же, проверено на синтетике).

## Приёмка на проме

Портфель и точное число людей по банку и сегментам (`res["journal"]`) сверяются с
payroll_bank_yoy и разбором РГС: ведомости те же (`mis_data_payroll_m`), отбор тот же —
разница должна быть малой. Существенная разница — повод разобраться.
(`uzp_data_payroll_m` не подходит: на ней отбор relev за 2024 год даёт 0 строк.)

Посмотреть долю строк с `seg_src = 'ЕПК'`: если она заметна, ключи истории
сегментов (дата, номер организации, ГОСБ) не сходятся с ведомостями.

## Открытый контур

```
docker compose up -d uzp_pg          # из корня проекта
python -m ptf.synth                  # синтетика в схеме synth_ptf
```

Потом прогон в тетрадке с `SCHEMA = SCHEMA_T = "synth_ptf"`, `REPORT_MONTH = "2026-10"`
и последняя ячейка: сводка сверяется с независимым эталоном на Python
(`ptf/reference.py`) по каждой ячейке и с заложенными событиями (сезонники,
организация перестала платить, смена сегмента, разовые, «мигающие» и т.д.).

## Стенд сторожа

Ячейка «Стенд сторожа» в тетрадке закладывает в реальное поколение события с известным
ответом (уход, остановка организации, провал на месяц, приход, реорганизация,
совместительство, смена кодов) и артефакты (календарь, недогруз ТБ, смена ГОСБ) и
проверяет, что детектор находит первые и молчит на вторых. Пороги приёмки — в
`bench.ACCEPT`. Соперник — простое правило «дальше всего от своей медианы»; сторож
(`ptf/watch.py`) сравнивается с ним по полноте, ложным тревогам и артефактам.
Ячейка «Сторож: карточки» показывает, что сторож нашёл в последних месяцах. `known_cases.csv` — известные случаи; на них сторож
не настраивается, только сдаёт экзамен.

Текущий стенд — **протокол 3**. Его числа нельзя напрямую сравнивать с прежними:

* Карточка должна появиться или материально усилиться относительно исходного фона
  и относиться к изменяемому потоку. Существовавшая карточка другого потока не засчитывается.
* Размер события измеряется по шуму изменяемого потока. Помимо запросов на 3/4/6 шумов
  проверяются 300/1000/3000 человек. Если минимальный размер увеличил событие,
  приёмка использует фактический размер в шумах, а не запрошенный.
* Изменения организаций распределяются по реальным ячейкам в месяце события.
  Размер когорты ограничен доступным остатком; ошибки закладки сохраняются и проваливают приёмку.
  Полная остановка проверяется в последнем месяце, чтобы не подменять будущую динамику
  организации вычитанием фиксированного числа людей из всех будущих месяцев.
* Когорта атома, не меняющая крупные организации, ограничена остатком вне них.
  Полный атом и «прочие организации» сравниваются с фоном своей совокупности.
* «Смена ГОСБ» сохраняет организацию, сегмент и ТБ и меняет именно ГОСБ.
* На реальных данных число карточек исходного фона — справочный показатель.
  Проверка «не более пяти ложных» применяется только к заведомо чистой синтетике.

Основные уровни используют полные исходные наблюдения. Параллельно проверяется
остаток атома вне крупных организаций по их фактическим ячейкам. Такая карточка
подписана «прочие организации»; её нельзя складывать с полным атомом.
Положительные прогнозные интервалы учитывают собственный и групповой разброс;
историческое большое событие не задаёт общий порог. Методика — [methodology.md](methodology.md).
Повторная карточка убирается, если уже показанные события того же направления
объясняют не менее 70% отклонения, целиком входят в её территорию в данном месяце,
а необъяснённый остаток уже не проходит порог значимости.
Главная ячейка организации не доказывает такое вложение: организация может работать
в нескольких ГОСБ. При неизвестной привязке карточки сохраняются; их значения могут
пересекаться и не предназначены для сложения между уровнями.
Для смены ГОСБ используются фактические потоки организации по ячейкам из поколения.
Паруются противоположные изменения в разных ГОСБ одного сегмента и ТБ; обычный
встречный оборот внутри одной ячейки не создаёт такую пару. Распознавание не зависит
от прохождения шумного итога организации через общий порог или от выбора главного
потока её карточки. Объяснение распространяется также на банк и сегменты, сохраняя
значимые независимые остатки. Это объяснение по агрегатам, не доказательство
административной перекодировки: для такой проверки нужны известные случаи.

В карточках «факт» — исходное число из поколения. Для прихода извне ожидание включает
возвраты после провала, которые исключены из сигнала сторожа. Общая добавка временных
уходов выделяется только при согласованном росте в большинстве ТБ и росте одиночных
выплат. Локальный провал организации остаётся сигналом. Последний месяц без наблюдаемого
возврата этой поправкой не снимается. «Отклонение вклада в
портфель» показывает разницу с ожиданием со знаком влияния потока, а не изменение
всего портфеля. Направление разницы указано в колонке «что».

### Запуск в Jupyter на DataLab

Для бизнес-разбора запускается **только ячейка «Бизнес-разбор портфеля»** перед стендом.
Она использует `panel` в памяти; если его нет — читает готовое поколение.
Сборка таблиц и стенд не запускаются. `BUSINESS_MONTH = None` выбирает крупнейшее
изменение банка или его частей; конкретный месяц можно указать явно.
`BUSINESS_PAGE`: 1 — итог, 2 — люди и история, 3–5 — срезы, 6 — организации,
7 — исходные потоки и проверки. Все строки сохраняются в `output/business/report.html`.
Календарная причина пока автоматически не устанавливается.

Для проверки сторожа используются две обычные ячейки той же тетрадки:

1. **«Стенд сторожа: приёмка и полный отчёт»** — перечитывает готовое поколение,
   перезагружает обновлённые модули, запускает сравнение и сохраняет отчёт.
2. **«Сторож: результаты для фотографирования»** — показывает уже рассчитанный
   результат небольшими страницами. `PHOTO_SECTION` выбирает раздел, `PHOTO_PAGE` —
   страницу, `PHOTO_MONTH` — месяц карточек (по умолчанию последний).

Обе ячейки находятся в основной `portfolio_core.ipynb`, которая включена в архив
обновления. Они используют `CONN` из параметров этой тетрадки. Ячейки параметров
и сборки подложки не изменены. Для проверки сторожа запускаются эти две ячейки
по порядку.

Результаты из закрытого контура передаются фотографиями экрана. Экспортировать файлы
для разбора не требуется. Все организации в карточках, диагностике и сохранённых
HTML/JSON заменены условными кодами `Орг. R…`; исходные номера в эти коды не входят.
У старого результата номера маскируются при просмотре новой ячейкой. Код строки
постоянен внутри поколения, но не предназначен для сравнения разных поколений.

Разделы просмотра: `итог`, `карточки`, `пропуски`, `календарь`, `качество`, `пороги`.
Смена страницы использует результат в памяти. Раздел `пороги` один раз разбирает
историю по уже загруженному `panel`, затем использует кэш. Он не обращается к БД,
не собирает подложку и не повторяет стенд. Страница 1 показывает пороги потоков,
страница 2 — источники порога самого проблемного сохранённого пропуска.
По умолчанию просмотр открывает `итог`, страницу 1. Дополнительные фотографии
старых порогов не требуются. После перезапуска ядра можно читать сохранённый отчёт.
Для повторного разбора старой калибровки остаётся раздел `пороги` со старым правилом
и явной подписью. Старый count-z и новый log-z имеют разные шкалы.

Промышленная сборка с точными возвратами уже выполнена. После исправления артефактов
от 06.11 повторно запускать сборку **не нужно**. Обновите пакет и выполните только
ячейку «Стенд сторожа». Сохранённое ядро не перезапускайте: если последняя ошибка
относится к артефакту и модель не менялась, завершённые события и эхо восстановятся.
Иначе стенд перечитает готовое поколение и пересчитает проверку, без сборки таблиц.

Нужны фотографии итога сторожа и страницы 7 бизнес-разбора (`BUSINESS_PAGE = 7`).
Страница 1 бизнес-разбора за январь уже получена. Организации маскируются автоматически.

Исторические кейсы — [known_cases.csv](known_cases.csv).
Раздел `кейс-август` разбирает C01 по панели в памяти: страницы 1–2 — портфель
и признаки, страница 3 — качество и коррекции. Год задаётся через `CASE_YEAR`.

`output/watch_acceptance/report.html` — полный отчёт без сети: критерии, все карточки,
соперник на тех же событиях, лишние сигналы артефактов и разбор крупнейших пропусков.
`report.json` содержит те же числа, идентификатор поколения, размеры панели и хеши
файлов для воспроизводимости. Параметры подключения в отчёт не записываются.
Даже при невыполненных критериях файлы сохраняются. Просмотр старого отчёта и
бизнес-разбор не требуют сборки; применение точных возвратов в новом стороже требует
обновлённого поколения. Промышленная приёмка остаётся открытой до общего прогона.
Файлы остаются внутри контура. Метод расчёта и чтения порогов — [methodology.md](methodology.md).

### Локальная проверка

Из этой папки:

```bash
python3 -m unittest discover -s tests -v
python3 -c 'from ptf import selfcheck; selfcheck.run_all()'
python3 -m ptf.validation --output output/watch_validation
```

Последняя команда проверяет пять панелей с независимыми seeds: обычную, несколько
ГОСБ у организаций, повышенный шум, события в прошлой истории и меняющийся состав
причин ухода. На каждой сохраняются
полный отчёт и сравнение с соперником. Код возврата 1 означает, что хотя бы один
критерий не выполнен; его нельзя трактовать как успешную приёмку.
Ограничения и результаты текущей версии — `VALIDATION.md`.

## Устройство

```
ptf/sql.py        весь SQL
ptf/build.py      прогон: справочники → тройки → люди → метки → остатки → сводка → проверки
ptf/segments.py   сведение сегментов (история и ЕПК)
ptf/selfcheck.py  самопроверки и сверка с синтетикой
ptf/reference.py  независимый эталон на множествах (только синтетика)
ptf/synth.py      синтетика
ptf/enrollment_type.csv  справочник видов зачислений (выгрузка с прома) — для синтетики
ptf/inputs.py     входы сторожа: панель атомов и крупных организаций из поколения
ptf/bench.py      стенд сторожа: фон, закладка событий и артефактов, метрики, соперник
ptf/watch.py      сторож: ожидание по другим ТБ, шум с «комками», отбор по нижней границе
ptf/acceptance.py единый отчёт приёмки HTML + JSON с диагностикой
ptf/validation.py локальная приёмка на четырёх панелях
known_cases.csv   известные случаи — экзамен сторожа (черновик, дополняется аналитиком)
```

Папка автономна: ничего не импортирует из проекта, переносится как есть.
