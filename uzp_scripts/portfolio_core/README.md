# portfolio_core — единая подложка портфеля ФЛ

Раз в месяц читает ведомости за последние 36 месяцев, размечает, что случилось с
каждым получателем ЗП, и хранит результат сводкой «месяц × id орг × ГОСБ». Любой
вопрос про портфель отвечается запросом к сводке — без нового чтения ведомостей.

Что и как считается — [DESIGN.md](DESIGN.md).

## Что появляется в БД

В `s_grnplm_ld_salesntwrk_pcap_sn_t_uzp`:

| Таблица | Что это |
|---|---|
| `yva_ptf_month_org` | сводка: 80 столбцов, строка = месяц × id орг × ГОСБ. Пересоздаётся каждым прогоном |
| `yva_ptf_flow_pairs` | потоки людей «организация → организация» к прошлому месяцу. Пересоздаётся |
| `yva_ptf_journal` | журнал: итоги и точное число людей по банку, ТБ, сегментам — по каждому прогону. Копится |
| `yva_ptf_vintage` | поколения: ключевые меры на дату прогона по срезам и крупным организациям. Копится |

Старая таблица `yva_ptf_runs` (журнал этапа 1) больше не пишется — её можно удалить.

Людей в постоянных таблицах нет: всё, где есть `epk_id`, живёт только во временных
таблицах прогона. Сводка и потоки подменяются одной транзакцией, **только если сошлись
все самопроверки**; иначе старые остаются, а новые лежат в `_new` для разбора.

## Как запускать

Тетрадка `portfolio_core.ipynb`, по ячейкам сверху вниз:

1. Самопроверки — секунды. Не прошли — дальше нельзя.
2. Параметры и запуск. `REPORT_MONTH` задаётся явно — последний закрытый месяц.
3. Итоги: проверки, портфель по месяцам, пересчёт прошлого, самые долгие шаги.
4. Примеры запросов к сводке.

Начало окна считается само: последние `N_MONTHS`, но не раньше 2023-11.
Лимит на оператор — `SQL_TIMEOUT_MIN = 60`. Если оператор всё равно упал по
таймауту на шагах «Метки движений» или «Остатки» — `EPK_CHUNKS = 4` (результат тот
же, проверено на синтетике).

## Приёмка на проме

Портфель и точное число людей по банку и сегментам (`res["journal"]`) сверяются с
payroll_bank_yoy и разбором РГС: ведомости те же (`mis_data_payroll_m`), отбор тот же —
разница должна быть малой. Существенная разница — повод разобраться.
(`uzp_data_payroll_m` не подходит: на ней отбор relev за 2024 год даёт 0 строк.)

Посмотреть долю строк с `seg_src = 'ЕПК'`: если она заметна, ключи истории
сегментов (дата, номер организации, ГОСБ) не сходятся с ведомостями.

## Открытый контур

```
docker compose up -d uzp_pg          # из корня проекта
python -m ptf.synth                  # синтетика в схеме synth_ptf
```

Потом прогон в тетрадке с `SCHEMA = SCHEMA_T = "synth_ptf"`, `REPORT_MONTH = "2026-10"`
и последняя ячейка: сводка сверяется с независимым эталоном на Python
(`ptf/reference.py`) по каждой ячейке и с заложенными событиями (сезонники,
организация перестала платить, смена сегмента, разовые, «мигающие» и т.д.).

## Стенд сторожа

Ячейка «Стенд сторожа» в тетрадке закладывает в реальное поколение события с известным
ответом (уход, остановка организации, провал на месяц, приход, реорганизация,
совместительство, смена кодов) и артефакты (календарь, недогруз ТБ, смена ГОСБ) и
проверяет, что детектор находит первые и молчит на вторых. Пороги приёмки — в
`bench.ACCEPT`. Соперник — простое правило «дальше всего от своей медианы»; сторож
(`ptf/watch.py`) обязан его обойти. Ячейка «Сторож: карточки» показывает, что сторож
нашёл в последних месяцах. `known_cases.csv` — известные случаи; на них сторож
не настраивается, только сдаёт экзамен.

Факты и ожидания всех уровней рассчитываются без вычитания событий организаций из
атомов. Повторная карточка убирается, если уже показанные события того же направления
объясняют не менее 70% отклонения, целиком входят в её территорию в данном месяце,
а необъяснённый остаток уже не проходит порог значимости.
Главная ячейка организации не доказывает такое вложение: организация может работать
в нескольких ГОСБ. При неизвестной привязке карточки сохраняются; их значения могут
пересекаться и не предназначены для сложения между уровнями.
Для смены ГОСБ используются фактические потоки организации по ячейкам из поколения;
её ожидание распределяется по историческим долям потока. При короткой истории из
местного потока вычитается всё ожидание организации. Принимающая ячейка не выбирается
по чужому всплеску. Объяснение сменой ГОСБ распространяется также на банк и сегменты.

В карточках «факт» — исходное число из поколения. Для прихода извне ожидание включает
возвраты после провала, которые исключены из сигнала сторожа. «Отклонение вклада в
портфель» показывает разницу с ожиданием со знаком влияния потока, а не изменение
всего портфеля. Направление разницы указано в колонке «что».

После обновления `ptf/inputs.py`, `ptf/bench.py`, `ptf/watch.py` и тетрадки достаточно
запустить «Стенд сторожа», затем «Сторож: карточки». Стенд перечитает существующее
поколение и подхватит новые модули. Новый прогон подложки для этой правки не нужен.
Регрессионные проверки без БД: `python3 -m unittest discover -s tests -v` из этой папки.

## Устройство

```
ptf/sql.py        весь SQL
ptf/build.py      прогон: справочники → тройки → люди → метки → остатки → сводка → проверки
ptf/segments.py   сведение сегментов (история и ЕПК)
ptf/selfcheck.py  самопроверки и сверка с синтетикой
ptf/reference.py  независимый эталон на множествах (только синтетика)
ptf/synth.py      синтетика
ptf/enrollment_type.csv  справочник видов зачислений (выгрузка с прома) — для синтетики
ptf/inputs.py     входы сторожа: панель атомов и крупных организаций из поколения
ptf/bench.py      стенд сторожа: фон, закладка событий и артефактов, метрики, соперник
ptf/watch.py      сторож: ожидание по другим ТБ, шум с «комками», отбор по нижней границе
known_cases.csv   известные случаи — экзамен сторожа (черновик, дополняется аналитиком)
```

Папка автономна: ничего не импортирует из проекта, переносится как есть.
