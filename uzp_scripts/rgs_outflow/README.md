# rgs_outflow — отток бюджетной сферы: ведомства, территории, причины, прогноз

Отвечает на вопрос: **где основной отток клиентов бюджетной сферы (РГС), в каких
ведомствах, что с ним происходит, чем отличаются территории и регионы, какая
часть падения — сокращение штата, а какая — уход к конкуренту, и какой будет
численность до конца года.**

Результат — один самодостаточный HTML-файл, открывается без сети.

## Постановка

| Вопрос | Решение |
|---|---|
| Ведомство | Отдельного поля нет ни в одной витрине. Выводится правилами по наименованию организации + флаг `is_force` + подсказка по отрасли. Неразобранное имя идёт в «Не классифицировано» и по ведомствам не распределяется. |
| Макропоказатели | Только внутренние прокси витрин банка (численность, штат, проникновение, средняя ЗП, план/факт). Внешних источников в закрытом контуре нет, и раздел подписан как прокси, а не как госстатистика. |
| Причина оттока | Падение численности раскладывается на «сокращение штата» и «уход к конкуренту» по поведению ШТАТА организации. Раскладка аддитивна: части всегда равны падению. |
| Прогноз | Аддитивный каркас `база − отток + приход`, три сценария из одной истории. Приход выводится из динамики численности, а не берётся колонкой витрины. |
| Тексты выводов | LLM с обязательным фолбэком на правила. Названия подразделений, регионов и организаций в модель не уходят — только токены. |

## Чего этот отчёт не сделает

* **Не скажет, в какой именно банк ушли люди по всей базе.** Банк-конкурент
  известен только по ключевым клиентам; доля покрытия печатается и подписывается.
* **Не измерит занятость и сокращения по региону в целом** — только по
  организациям, которые являются клиентами банка.
* **Не построит тенденции, если истории нет.** Разведка проверяет глубину в трёх
  витринах; если месяцев не хватает, блоки тенденций и прогноза не строятся, и
  это написано в отчёте.
* **Не даст обещание по будущему.** Прогноз — расчёт по истории, он не знает о
  решениях, принятых после отчётного месяца.

## Куда класть папку

Каталог должен лежать **внутри** проекта — рядом с `uzp_dash` или глубже: пакет
ищется вверх по дереву, конкретный уровень вложенности значения не имеет. Если
папка лежит отдельно, путь задаётся переменной окружения:

```python
import os
os.environ["UZP_DASH_ROOT"] = "/путь/к/dashboards"
```

## Как запускать

1. Открыть `rgs_outflow.ipynb`.
2. Ячейка 2 — установка библиотек с внутреннего зеркала (раскомментировать при
   первом запуске; `requirements.txt` лежит в этой же папке).
3. Ячейка 3 — список доступных моделей LLM. Выбранная модель должна быть в нём.
4. Ячейка 4 — самопроверки, ~1 секунда. Не прошли — дальше идти нельзя.
5. Ячейка 5 — параметры и прогон, 1–3 минуты плюс ~5 вызовов модели.
6. Ячейки 6–8 — посмотреть цифры, проверить фолбэк, увидеть, что отправлять.

**Отчётный месяц задаётся явно** (`REPORT_MONTH = "2026-07"`). Пустое значение
допускается, но берёт последний месяц витрины — а в начале месяца это уже
незакрытый месяц, и по готовому файлу это незаметно.

Если модель возвращает пустой ответ с `finish_reason='length'` — она думающая:
весь бюджет уходит в `reasoning_content`. Параметр `LLM_EXTRA` в ячейке 5
отключает размышления; это проверено в открытом контуре.

## Что отправлять наружу

| Файл | Наружу |
|---|---|
| `rgs_outflow_ГГГГММ_*.html` | **да** — самодостаточный, без сети, слово-идентификатор заменено на «Орг.» |

## Устройство

```
rgs_outflow/
├── rgs_outflow.ipynb   запуск и параметры (логики нет)
├── requirements.txt    рядом с тетрадкой — обязательно
├── METHODOLOGY.md      формулы, SQL, примеры в числах, ограничения
└── rgs/
    ├── __init__.py     поиск пакета uzp_dash вверх по дереву
    ├── queries.py      весь SQL; _GMAP и словарь сегментов берутся из дэша
    ├── probe.py        разведка витрин -> probe.json, список ограничений
    ├── fetch.py        выгрузка: лимит строк, чанкование, счётный запрос
    ├── agency.py       классификатор ведомств по наименованию
    ├── analyze.py      ведомства, тенденции, территории, ПРИЧИНЫ, макро, конкуренты
    ├── forecast.py     прогноз численности, три сценария
    ├── prompts.py      промпты (только обезличенные токены)
    ├── narrative.py    вызов LLM, фолбэк на правила, защёлка отказа шлюза
    ├── view.py         сборка HTML, инлайновый SVG вместо библиотек графиков
    ├── run.py          оркестратор и DEFAULTS
    └── selfcheck.py    13 самопроверок до обращения к БД
```

## Что переиспользуется, а не написано заново

`uzp_dash.db` (подключение, `statement_timeout`, перехват Kerberos),
`uzp_dash.config` (контур, схемы, `.env`), `uzp_dash.progress` (прогресс и логи
LLM), `uzp_dash.anonymize` (псевдонимы для промпта), `uzp_dash.llm` (единая точка
вызова модели), `uzp_dash.render` (тема, компоненты, замена слова-идентификатора),
`tb_health.queries._GMAP` (соответствие ГОСБ) и `tb_health.segments` (словарь
сегментов). Вторая копия любого из этих механизмов разъехалась бы молча.

## Открытый контур

Синтетика повторяет промышленную схему точь-в-точь, поэтому SQL переносится
буквально, и в коде нет ни одного ветвления «если пром». Под этот отчёт
синтетика расширена: бюджетные наименования организаций, колонки ОКТМО
(вместе с мусором в `oktmo_subject_code`, как на проме), витрина ключевых
клиентов с банками-конкурентами, регионы с разным характером оттока.

Прогон на синтетике проверяет **механику, а не точность**: он показывает, что
все ветки алгоритма отрабатывают, а не что прогноз верен.
