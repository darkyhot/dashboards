# payroll_rgs_cohort — почему численность бюджетной сферы упала год к году

Отвечает на вопрос: **сколько ФЛ перестали и сколько начали получать зарплату в
РГС, сколько получателей убавилось из-за совместителей; когда это произошло;
почему; и где.**

Разбор идёт **до физического лица**: списки получателей сравниваются поимённо, и
каждое ФЛ, переставшее или начавшее получать, получает ровно одну ситуацию.
Агрегаты на это не отвечают в принципе — см. «Зачем» ниже.

Результат — два файла: HTML-отчёт для внутреннего чтения и **обезличенный**
markdown-документ, который можно отправить наружу на разбор.

## Зачем, если есть агрегаты

| Агрегат показывает | Чего он не показывает |
|---|---|
| Доля совместителей упала с 7% до 5% | Метрика считается **тройками** (человек, организация, подразделение) — падение доли само по себе даёт часть минуса. Сколько именно, агрегат не отвечает. |
| «Утекло образование» | Ушли ли люди или перестали считаться пары. Это разные события с разными решениями. |
| «Утёк такой-то холдинг» | Организацию могли переоформить: люди те же, номер другой. Агрегат покажет это как отток, потому что новый номер к старому холдингу ещё не привязан. |
| Численность упала на N | Упала одним месяцем или равномерно за год. По двум точкам это неразличимо, а вывод из них — противоположный. |

## Постановка

| Вопрос | Решение |
|---|---|
| Что такое «получатель» | **Тройка (человек, организация, подразделение банка)**. Тройка засчитывается, если сумма зачислений **в организацию** за месяц строго больше **2500 ₽** по заданному списку из 18 кодов. Порог считается по организации, а получатели — по тройкам: это разные грейны, и так задано постановкой. Второй вариант порога (по подразделению) разведка печатает рядом, чтобы можно было сверить с отчётностью, а не спорить. |
| Сегмент организации | Текущий срез `uzp_data_epk_consolidation`: отчётной даты в этой витрине нет вовсе. Один и тот же список организаций применяется к обоим годам, поэтому перекоса год к году это не создаёт. |
| Ликвидация | «По номеру организации нет **ни одной** активной записи». Смотреть на одну строку нельзя: у одного номера бывает несколько ЕПК, и «Ликвидирована» на одной из них ничего не значит, пока жива другая. |
| Численность организации | Считается из ведомостей, а не берётся из витрины организаций. |
| Ведомство и уровень подчинения | Отдельных полей нет ни в одном разрешённом источнике — выводятся правилами по наименованию (`uzp_dash/agency.py`, `cohort/level.py`). Неразобранное имя идёт в «Не классифицировано» и по группам не раскидывается. |

Источники — только три: `uzp_data_payroll_m`, `uzp_data_epk_consolidation`,
`uzp_dim_gosb`.

## Как читается результат

Два определения, одни на весь отчёт:

* **Получает зарплату в РГС** — у ФЛ в этом месяце есть бюджетная организация, от
  которой зарплатные зачисления за месяц больше 2 500 ₽.
* **Получатель** — строка счёта: ФЛ × организация × ГОСБ. Совместитель в двух
  организациях — два получателя.

Изменение раскладывается **одним и тем же** способом в шапке, в таблицах, в
документе и в промптах (`analyze.decomposition`):

```
Получателей год назад
− Перестали получать зарплату в РГС                       (ФЛ: −n)
+ Начали получать зарплату в РГС                          (ФЛ: +m)
± Совместители остались в РГС, но стали получать
  в меньшем числе организаций                             (ФЛ: 0)
= Получателей в отчётном месяце
```

Других разложений в отчёте нет. Раньше их было три (ещё «чистое изменение» без
третьей строки и формула «людей стало меньше / совместительство схлопнулось»), и
шапка не сходилась с таблицей под ней. Тождество проверяется в коде по
получателям и по ФЛ и печатается в отчёт.

**ФЛ перестало получать зарплату в РГС**, только если в отчётном месяце у него нет
ни одной бюджетной организации с зарплатой больше 2 500 ₽. Сменило организацию
или ГОСБ, осталось в одной организации из двух — **продолжает получать зарплату в
РГС**, и уходом это не считается: сегмент главное, а не территория и организация.

Почему перестали — ровно одна ситуация на ФЛ:

| Ситуация | Что значит |
|---|---|
| ФЛ больше не получает зачислений в банке | ни зарплаты, ни других выплат (про вклады и карты ведомости не говорят) |
| ФЛ получает зарплату в банке, но от небюджетной организации | зарплата больше 2 500 ₽ есть, организация не из РГС |
| От бюджетной организации приходят только незарплатные выплаты | пенсия, пособия, расчёт |
| Зарплата от бюджетной организации меньше 2 500 ₽ за месяц | зарплатные зачисления есть, но малы |

Почему начали — зеркально: раньше не получал зачислений в банке; раньше получал
зарплату от небюджетной организации; раньше приходили только незарплатные
выплаты; зарплата выросла выше 2 500 ₽.

## Почему стало меньше совместителей

```
Изменение получателей = изменение ФЛ + изменение совместительства
```

Совместитель в трёх организациях — один ФЛ и три получателя, два «лишних».
Изменение совместительства раскладывается на три части, которые берутся из тех
же чисел, что шапка: совместители перестали получать, совместители среди
начавших, и оставшиеся в РГС стали получать в меньшем числе организаций или ГОСБ.

Дальше раздел отвечает, **уход ли это людей**:

* **как устроено совместительство** — «лишние» получатели из-за нескольких
  организаций против «одна организация через несколько ГОСБ». Второе — чистый
  эффект счёта: организация свела выплаты в один ГОСБ, человек ничего не менял;
* **что случилось с местом работы** у оставшихся в РГС: та же организация через
  другой ГОСБ; организация больше не платит зарплату в РГС никому (закрытие,
  слияние); зарплата до 2 500 ₽; только незарплатные выплаты; ушёл с места работы.
  Первые две — не уход человека. Итог по ситуациям = третьей строке шапки;
* списки организаций (переставшие платить — с тем, куда ушли их ФЛ; откуда ушли
  совместители) — под «+».

Всё считается поверх рабочего набора, без новых сканов витрины.

## Что проверяется сверх раскладки

* **Когда** — помесячный ряд за 25 месяцев; поиск месяцев-обрывов **по
  год-к-году, а не по соседнему месяцу**: в ряду, где январь проваливается каждый
  год, сравнение с соседом объявляет обрывом оба января, то есть выдаёт
  регулярный сезон за событие. Плюс сравнение отчётного месяца **с соседними и с
  тем же месяцем год назад** — без него вывод о годовой динамике строится по
  одной точке, а если отчётный месяц сезонная яма, эта точка врёт. Плюс вторая
  лестница «к предыдущему месяцу», кривая дожития и полнота загрузки партиций.
* **Порог** — как выглядит падение при порогах 0 / 1000 / 2500 / 5000 / 10000 ₽.
  Порог фиксирован, а зарплаты индексируются: сам по себе он должен год к году
  добавлять получателей. Сохраняется падение при нулевом пороге — порог ни при чём.
* **Какой вид выплаты просел** — только зарплатные коды, подписанные названием, с
  изменением к предыдущему месяцу и год к году. Метрика складывается из
  восемнадцати кодов, и провал одного вида выплаты (стипендия в каникулы, премия
  в конце квартала) выглядит падением численности, хотя человек никуда не ушёл: у
  него просто нет выплаты этого вида в этом месяце. Коды вне списка не считаются
  вовсе — они на метрику не влияют по построению, а в таблице заняли бы весь верх
  массовыми социальными выплатами и сбили бы вывод.
* **Куда делись люди** — в какой сегмент ушли и чем заменились их зарплатные
  зачисления. «Ушёл» без адреса — половина ответа: пенсия означает выход на
  пенсию, пособие на детей — декрет, расчёт при увольнении — увольнение. По
  каждому виду зачисления показываются организации, дающие больше всего людей
  (`codes_top_inn`, по умолчанию пять): «пособие на детей — четыре тысячи
  человек» решения не подсказывает, пока неизвестно, одна это организация или
  двести. Доля считается ВНУТРИ вида — вопрос в том, какую его часть даёт одна
  организация.
* **Почему ушли** — ушла организация целиком (увела зарплатный проект), ушла
  массово или люди уходят по одному; сменился ли договор зарплатного проекта;
  уходили обрывом или постепенно (постепенных можно было удержать); в каком месяце;
  сколько получали ушедшие по сравнению с коллегами по своей организации. Мотивов
  людей в разрешённых источниках нет — блок их не выдумывает.
* **Разрезы** (холдинги, ведомства, уровень, отрасль, ТБ, ГОСБы) — сколько
  перестали получать зарплату в РГС (по четырём ситуациям), сколько начали,
  переходы внутри РГС и совместители, и итоговое изменение. Сумма изменения по
  всем группам = изменению в шапке (строка «Итого»). Переключатель над таблицей:
  верх по переставшим или верх по изменению — это разные наборы групп, поэтому
  две таблицы, а не пересортировка. ГОСБ — номер из
  ведомостей, поэтому разрез строится всегда; справочник даёт только название, а
  не опознан — строка подписана «ГОСБ № …». Таблица организаций свёрнута под «+».
* **Графики** — ряд получателей и доля получателей базового месяца, получающих до
  сих пор: подписан каждый месяц (при длинном ряде — через один, базовый и
  отчётный всегда), деления по оси Y, подсказка с числом у каждой точки.
* **Сезонность** — только при ПОВТОРЕ год к году: человек получал в предыдущем
  месяце оба года и не получал в отчётном оба года. Просто «был в прошлом месяце,
  нет сейчас» сезонностью не является — доказать, что он вернётся, нечем.
* **Стаж ушедших** — сколько месяцев человек был в сегменте до ухода. Уходят
  недавно пришедшие — это ротация; уходят старожилы — это потеря ядра.
* **Переоформление** — организации, чьи люди дружно оказались в одном и том же
  новом номере. Порог задан по **доле** потерь организации, а не по числу людей:
  двадцать человек из двадцати и двадцать из двух тысяч — разные события.

## Чего этот отчёт не сделает

* **Не скажет, в какой банк ушли люди** — в разрешённых источниках такого поля нет.
* **Не отличит увольнение от смены работодателя** вне клиентской базы банка:
  человек, которого нет в ведомостях, в обоих случаях выглядит одинаково.
* **Не восстановит сегмент на дату** — только текущим срезом. Переклассификация
  организации между годами в разбор не попадёт.
* **Не учтёт организации с непригодным номером** — доля таких строк считается
  помесячно и печатается; если она выросла год к году, часть «падения»
  произошла в сопоставлении, а не в жизни.

## Запуск

```
payroll_rgs_cohort.ipynb   # порядок ячеек обязателен
```

Ячейка 4 — самопроверки без БД, ячейка 5 — параметры и прогон. Отчётный месяц
задаётся **явно**: автовыбор «последний месяц витрины» в начале месяца взял бы
незакрытый месяц, и заметить это по готовому файлу невозможно.

## Как проверить любую цифру

У каждого блока отчёта — значок **i**, раскрывающий SQL, которым посчитаны его
цифры, со значениями параметров в шапке. Показывается **самодостаточная** форма
запроса: на проме разбор идёт по временным таблицам, и текст `FROM t_pairs`
читателю выполнить негде — таблица жила внутри чужой сессии. Определения выборок
инлайнятся, и запрос можно скопировать и выполнить как есть.

Текст берётся из ФАКТИЧЕСКОГО исполнения, а не собирается заново: вторая сборка
молча разъехалась бы с исполнением, и отчёт предъявлял бы запрос, которым цифра
не считалась. В обезличенный документ те же запросы уходят приложением в конце.

## Что можно отправлять

| Файл | Наружу |
|---|---|
| `payroll_rgs_cohort_*.md` | **можно** — обезличен: названия заменены токенами, номера удалены, цифры сохранены |
| `payroll_rgs_cohort_*.html` | нет — в нём настоящие наименования |
| `probe.json`, `run_config.json` | нет — для разбора прогона |
| `output/llm_logs/` | нет — там полные промпты с данными витрин |

Обезличивание не декларируется, а **проверяется**: готовый текст сверяется с
каждым настоящим названием из данных, и при единственном совпадении файл не
пишется вовсе. Документ, который «почти обезличен», хуже отсутствующего — его
отправят.

## Устройство

| Файл | Что внутри |
|---|---|
| `cohort/queries.py` | весь SQL, ни одной строки SQL за его пределами |
| `cohort/probe.py` | разведка: имя колонки кода, глубина ряда, полнота партиций, пригодность номеров |
| `cohort/fetch.py` | рабочий набор (временные таблицы либо CTE) и выгрузка |
| `cohort/analyze.py` | раскладка, ряды, дожитие, разрезы, проверки сходимости |
| `cohort/level.py` | уровень подчинения по наименованию |
| `cohort/view.py` | HTML и значок «i» с запросом у каждого блока |
| `cohort/report_text.py` | обезличенный документ и проверка утечки |
| `cohort/narrative.py`, `prompts.py` | тексты выводов с фолбэком на правила |
| `cohort/selfcheck.py` | 37 проверок без БД (в том числе: одно разложение в шапке и документе, нет устаревших терминов, ГОСБ без справочника) + проверка против синтетики |
| `cohort/run.py` | оркестратор |

Классификатор ведомств (`uzp_dash/agency.py`), вызов LLM с обезличиванием
(`uzp_dash/narrative.py`), доступ к БД и сборка HTML — общие с остальными
отчётами проекта. Второй копии этих механизмов быть не должно: они разъедутся
молча, и два отчёта про один сегмент начнут отвечать по-разному.

## Отладка снаружи

Синтетика открытого контура содержит `uzp_data_payroll_m` за 25 месяцев с
заложенными событиями: месяц-обрыв, смена кода зачисления у силовых организаций,
переоформление шести организаций, ликвидация, сползание части получателей ниже
порога, непригодные номера, **организации с двумя подразделениями и переводы
между ними**, а также **сезонные ямы в январе и августе** — без них проверка
сезонности не сработала бы ни разу и уехала бы на пром непроверенной. Ожидаемые ответы генератор пишет в
`output/synth_payroll_expect.json`, и `selfcheck.check_against_synth(res)`
требует, чтобы разбор нашёл каждое событие.

```bash
docker compose up -d
python3 -m synth
```

Затем прогон тетрадки с `CONTOUR="open"` и `REPORT_MONTH="2026-06"` (ряд
синтетики заканчивается июнем 2026).
