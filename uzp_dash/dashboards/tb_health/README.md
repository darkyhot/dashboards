# Дэш `tb_health` — «что плохо у ТБ и что можно сделать»

Управляющему ТБ: выполняется ли план ТЕКУЩЕГО месяца и как на это повлиять,
пока месяц не кончился.

## Файлы
- `queries.py` — SQL к 7 таблицам (метрики 1000164 ФОТ, 12400196 получатели).
- `forecast.py` — модель прогноза на текущий месяц (чистые функции над DataFrame).
- `analyze.py` — бизнес-логика: провальные ТБ→ГОСБ→сегменты, разрыв до плана,
  отбор организаций (потенциал × средняя ЗП), классификация по воронке.
- `prompts.py` — промпты нарратива для LLM.
- `view.py` — apple-вёрстка страницы.

## Прогноз и управление портфелем (главное)
Окончательная ЗП-ведомость есть только за ЗАКРЫТЫЙ месяц, поэтому дэш показывает не
факт, а прогноз. **Прогноз он не считает** — берёт готовым из витрины метрик,
колонка `uzp_dwh_metrics.prediction_amt`, на всех уровнях (`sb`/`tb`/`gosb`) и во всех
разрезах по сегментам. Выполнение = `prediction_amt / plan_amt`.

**Опорные даты.** `ref_cur` — самый свежий месяц, на который в витрине уже есть
`prediction_amt` (или параметр `report_month`); `ref_closed = ref_cur − 1` — портфель-база;
`ref_funnel = ref_cur`. Если прогноза нет вовсе — фолбэк на закрытый месяц витрины
организаций + 1, о чём дэш пишет в прогрессе.

**Фактический отток** — `uzp_dwh_fact_outflow` за ТРИ ЗАКРЫТЫХ месяца (T-1, T-2, T-3)
при `outflow_qty >= 3`, за вычетом вернувшихся из `uzp_data_outflow_return_detail`
(join по `report_dt`, `gosb_id`, `inn`):

    невозвращённый отток = max(outflow_qty − COALESCE(return_qty, 0), 0)

Порог в 3 человека — требование бизнеса: уход одного-двух это текучка, а не потеря
клиента. Сколько срезает порог, печатается в прогресс.

**Пайплайн** — `yva_pl_task_deal_code` (схема `{schema_t}`, ключ
`coalesce(deal_code, task_code)`): в воронке `plan_staff_deal_qty` размазан на все
3 месяца жизни сделки, помесячная разбивка есть только здесь. Показываем два числа: с
поправкой на историческую реализуемость сделок и «если отработают на 100%».

**Блок «Управление портфелем»** — три НЕЗАВИСИМЫХ факта, а не разложение прогноза:
портфель закрытого месяца, невозвращённый отток за 3 месяца, пайплайн на месяц. Они
не складываются в прогноз и сверять их сумму с ним бессмысленно.

**Два рычага** в списке организаций: «Привлечь» (потенциал минус пайплайн) и «Вернуть»
(невозвращённый отток). Эффект привлечения уменьшается на пайплайн — защита от двойного
счёта: приход по сделкам уже заложен в прогноз витрины.

**Закреплённый сотрудник** — столбец «Сотрудник» в списке к работе: кому поручить.
`uzp_data_emp_epk_assignment` (`role_id = 14`, `end_dttm IS NULL`) → ЕПК
(`uzp_data_epk_consolidation`, оттуда ИНН) → штатка (`uzp_dwh_sap_staff_emp`, ФИО за
максимальную дату, где оно заполнено). На пару (ГОСБ, организация) берётся последнее
закрепление по `start_dttm`; где действующего нет — прочерк, покрытие печатается в
прогресс. В LLM ФИО не уходит.

**Чего больше нет.** Удалены собственная модель оттока (сезонность, устойчивость,
разовость), ежедневная витрина `uzp_dwh_day_outflow` и рычаг «Удержать»: предсказывать,
кто уйдёт в текущем месяце, больше нечем — отчёт говорит о случившемся.

## Логика (Этап 2)
1. По ТБ — метрики ФОТ и получателей, `period_type='m'`,
   `extended_dim_1=1` (все сегменты): план берётся за ТЕКУЩИЙ месяц, факт заменён
   прогнозом, ранг ТБ — за закрытый месяц (в текущем факт витрины частичный).
2. Разложить по входящим ГОСБ (`uzp_dim_gosb`: `tb_id`→`old_gosb_id`→`new_gosb_name`)
   и по сегментам (`extended_dim_1 ∈ 20..25`) → где провал.
3. По провальным ГОСБ — `uzp_dwh_company_holding_metric`: организации с макс.
   потенциалом привлечения (`fot_potential_amt`) и оттоком (`fot_outflow_amt`),
   пересчёт в ФОТ через среднюю ЗП (`current_fot_amt/current_fl_qty`).
4. Сверка с `uzp_dwh_sale_funnel_task` по `inn`: работали ли, результат отработки
   → 2 группы: «с кем работать» и «с кем нет смысла и почему».
5. Итог: сколько не хватает до плана + список организаций, закрывающий разрыв.

## Разделы дэша (ГОСБ-центричная структура)
1. Hero-вердикт по ПРОГНОЗУ получателей (выполнение, разрыв, сколько дней до конца
   месяца), ФОТ рядом; строкой ниже — закрытый месяц и ранг ТБ по нему.
2. Два KPI (получатели, ФОТ): план/прогноз/выполнение + мера.
3. **Управление портфелем**: портфель закрытого месяца · фактический отток за 3
   месяца, который не вернулся · пайплайн на месяц. Три независимых факта, НЕ
   слагаемые прогноза; рядом «если пайплайн отработают на 100%».
4. Матрица ГОСБ×сегмент по прогнозу витрины (тепловая карта) + топ вкладов в недобор.
5. **ГОСБ — что сделать по каждому**: карточки по ВСЕМ ГОСБ (включая выполняющие
   план — видно, за счёт чего он вытягивается), сортировка по недобору. Карточка =
   мера выполнения + таблица `прогноз / план / недобор / орг` в ОДНИХ колонках на
   двух уровнях: строка «Всего» по ГОСБ и строки ВСЕХ сегментов (западающие сверху,
   выполняющие ниже и приглушены). Разницу до итога закрывает строка «прочие» — она
   поглощает расхождение уровней `tb`/`gosb` (см. ниже), поэтому таблица всегда сходится.
   Ниже — итог привлечь/вернуть + эффект ФОТ и активности за 3 мес по этому ГОСБ.
6. **Разбор прогноза по клику** (оверлей `<dialog>`, Esc/клик по подложке закрывают).
   Порядок блоков — от числа к именам, потому что именами число объяснить НЕЛЬЗЯ:
   на тестовом ГОСБ отток 552 чел размазан по 67 организациям, топ-5 дают лишь 32%.
   Блоки: водопад этого ГОСБ · отток по ПРИЧИНЕ и по ЗОНЕ ВЛИЯНИЯ (можно работать /
   влиять нечем / вне эталонной базы) с выводом «реально ваши N чел по K орг» ·
   крупнейшие организации в оттоке (порог `DETAIL_MIN_SHARE`=5% блока и
   `DETAIL_MIN_FL`=3 чел, до `DETAIL_MAX_ROWS`=8 строк) с причиной и действием из
   аудита, хвост свёрнут в одну строку · пайплайн · тренд базы год к году ·
   таблица сегментов с добавленными колонками оттока и пайплайна.
7. **Организации к работе** — интерактивная таблица (поиск, в т.ч. по фамилии
   закреплённого сотрудника, + фильтры по ГОСБ, сегменту, рычагу + пагинация) на
   самодостаточном инлайн-JS.
8. Нет смысла работать — причина (правила + LLM по свободному тексту).
9. Динамика до плана: проекция `прогноз → +привлечь → +вернуть/удержать → план`.
10. Нарратив LLM «что плохо и что делать».

## Известное расхождение (не ошибка прогноза)
Сумма ячеек матрицы может не совпадать с итогом по ТБ: уровни `tb` и `gosb` в
витрине метрик — разные строки и совпадать не обязаны, плюс в справочнике ГОСБ
есть `old_gosb_id`, числящиеся сразу под ДВУМЯ `tb_id` (`_GMAP` относит такой ГОСБ
к меньшему). Дэш печатает величину расхождения в прогресс, а не прячет его.
Собственная арифметика прогноза (водопад) проверяется отдельно и обязана сходиться в ноль.

## Аудит отработки (что уходит в LLM)
Цель — одно умозаключение по каждой паре (ГОСБ, ИНН): есть ли смысл идти в
организацию; отработали качественно или «лишь бы закрыть»; нет ли противоречий между
сотрудниками; реально ли отработан отток / возможно ли привлечение.

- **Пул** (`analyze._audit_pool`): ВСЕ организации западающих сегментов их ГОСБ +
  добор из других сегментов ГОСБ (когда своих не хватает под 1.5× плана). Не «топ-N».
  Порог по эффекту `llm_min_impact`, жёсткий потолок вызовов `llm_max_calls` — хвост
  уходит на правила. Один глубокий проход (без волн).
- **Правила — первая линия** (`text_rules.py`): чек-лист → ключевые слова (regex +
  анти-отрицание). `no_point` детерминированно возможен ТОЛЬКО из структурного ответа
  чек-листа (ликвидация); «ликвидация/банкротство» по ключевым словам — лишь подсказка
  (`needs_llm`), подтверждает модель. Правила не закрывают кейс при ≥2 авторах и при
  «успех заявлен, а факт по старой сделке = 0» (`_POSITIVE_REASONS` → в LLM).
- **LLM** (`prompts.py`): по паре — ФАКТЫ витрины (сделки только «старый» месяц, свежие
  исключены) + хронология заметок с обезличенным автором (`Сотрудник-NN` по табельному,
  ФИО не тянем). Ответ: `verdict`, `quality` (качественно/формально/не отработана),
  `contradiction`, `outflow_worked`, `attract_real`, reason/action. Метка качества
  дописывается префиксом в поле «Причина / действие» (вёрстка не меняется).
  В ФАКТЫ входит фактический отток за 3 закрытых месяца с разделением «ушло /
  вернулось / потеряно» — организация, откуда ушли и вернулись, отработана, а та же
  цифра ухода без возврата означает потерю. Плюс «на текущий месяц в пайплайне
  запланировано N получателей — работа уже идёт»: снимает ложное «нужна активность».

## Статус
Этап 2 + аудит отработки + прогноз на текущий месяц — реализовано. LLM-вызовы устойчивы к сбоям (ретраи, лестница
дробления батча 12→10→3→1, фолбэк на правила). Контур — из тетрадки
(`generate_dashboard(contour=...)`); параметры аудита — `llm_batch`, `llm_min_impact`,
`llm_max_calls`.
