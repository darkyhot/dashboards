# SDD витрин УЗП — правила для агента

Здесь витрины УЗП описываются спеками OpenSpec, потом по ним пишутся DDL и plpgsql-функции
для Greenplum (ядро PostgreSQL 9.4). Python, DataLab и тетрадки здесь не используются.
Правила проекта portfolio_core (маскирование, `yva_`, DataLab, ячейки тетрадки) в этой папке
не действуют.

## Структура

```
openspec/
├── AGENTS.md, CLAUDE.md
├── knowledge/codestyle/      база знаний: код-стайл SQL и ETL (обязателен)
├── shared/
│   ├── config.yaml           общий конфиг OpenSpec для всех витрин
│   └── intent_template.md    шаблон файла интента
├── scripts/new_mart.sh       создать папку новой витрины
└── marts/<витрина>/
    ├── intents/              требования заказчика: 001-initial.md, 002-...md
    ├── openspec/             OpenSpec только этой витрины
    │   ├── config.yaml       → ../../../shared/config.yaml
    │   ├── specs/            как витрина работает сейчас
    │   └── changes/archive/  сделанные доработки
    └── sql/
        ├── ddl/              <таблица>.sql — актуальный DDL целиком
        ├── functions/        <функция>.sql — актуальная версия функции
        └── migrations/       NNN-<кратко>.sql — alter/пересоздание уже выведенной таблицы
```

Профили таблиц-источников — `../data/profiles/<схема>.<таблица>.profile.json`.

## База знаний

Код-стайл — [knowledge/codestyle/](knowledge/codestyle/), начинать с
[conventions.md](knowledge/codestyle/conventions.md) (таблица «Куда смотреть»):

- [naming.md](knowledge/codestyle/naming.md) — имена объектов и полей, глоссарий УЗП;
- [sql-style.md](knowledge/codestyle/sql-style.md) — оформление SQL, даты, функции-помощники;
- [target-tables.md](knowledge/codestyle/target-tables.md) — целевые и tmp-таблицы, параметры,
  статусы, лог, ККД;
- [templates/](knowledge/codestyle/templates/) — шаблоны DDL витрины и ETL-функции.

## Как работать

1. Витрины не смешивать. Команды `openspec` и скиллы `/openspec-*` запускать из папки
   `marts/<витрина>/` — тогда OpenSpec видит только её спеки и архив. Из корня `openspec/`
   OpenSpec витрин не видит. Если витрина не названа — спросить.
2. Новая витрина — `scripts/new_mart.sh <витрина>`.
3. Новый запрос заказчика — следующий по номеру файл в `marts/<витрина>/intents/` по шаблону
   `shared/intent_template.md`. Текст заказчика вставляется как есть и не правится; ответы на
   вопросы дописываются в «Уточнения» с датой.
4. Изменение: `/openspec-propose` по файлу интента → проверка пользователем →
   `/openspec-apply-change` → `/openspec-archive-change`. Имя change — `NNN-<кратко>`
   по номеру интента. После архивации в файле интента заполнить «Изменение OpenSpec».

## SQL-код и его версии

- Один объект — один файл, в файле всегда актуальная версия: функция целиком
  (`create or replace function` + `comment on function`), таблица — полный DDL с `comment on`.
  Старые версии не копируются рядом (`_v2`, `_old`) — история в git.
- Шапка функции, раздел «Изменения» (`target-tables.md`): строка на каждую доработку —
  `ГГГГ-ММ-ДД <ФИО>. <что изменено>. (<номер задачи>; интент NNN)`.
- Если меняется уже выведенная таблица (тип поля, новое поле), кроме правки `sql/ddl/`
  пишется скрипт перехода `sql/migrations/NNN-<кратко>.sql` с номером интента.
- Один интент — один коммит: интент, спеки, архив change и SQL вместе. Сообщение:
  `<витрина> NNN-<кратко>: <что сделано>`. История функции — `git log -p -- <файл>`.

## Чего не делать

- Не придумывать формулы, пороги, периоды и сравнения. Чего нет в интенте — спросить
  пользователя коротко и простыми словами, без вариантов-догадок.
- Не править текст заказчика в интентах.
- Коммит и push — только по просьбе пользователя.
