# Нейминг объектов и полей УЗП

Правила применяются, когда создаёшь новый объект или новое поле. Существующие имена и поля
не переименовывай: при расчёте опирайся на DDL и профиль конкретной витрины, а не на правило.

## Формула имени объекта

```
[бизнес-направление]_[проект]_{система-источник}_[тип сущности]_{система-источник}_[бизнес-сущность]
```

Обязательные токены — **тип сущности** и **бизнес-сущность**. Остальные — по ситуации.
Название таблицы не должно совпадать ни с одним из её столбцов.

### Токены департамента

| Токен | Значение |
| --- | --- |
| `uzp` | бизнес-направление «Управление зарплатных проектов» |
| `uzp_agent` | проект AI агент |

Направление `uzp` в имени стоит всегда, кроме перекладок без трансформации (см. таблицу ниже).
Проектный токен добавляется только для объектов проектного контура; витрины управления — без него
(`uzp_dwh_metrics`). Реестр проектных токенов перечисляет для нас ещё `uzp_dqc`, `uzp_fl` и `uzp_fl_ul`.

### Три варианта порядка токенов

| Ситуация | Порядок токенов | Пример |
| --- | --- | --- |
| Объект загружен из системы-источника без трансформации и используется всем блоком | `[источник]_[тип]_[сущность]`, бизнес-направление не ставится | `jupiter_data_agrmnt_num` — договоры из Юпитера |
| Команда редактирует объект: есть условие отбора, обогащение или расчёт | `[направление]_[проект]_[тип]_[источник]_[сущность]` | `uzp_dwh_sap_staff_emp` — расчёт по реплике SAP HR; цеховой пример `dsa_dim_asfs_login` |
| Источник — другие расчётные витрины Greenplum | токен источника пропускается | `uzp_dwh_fact_outflow`, `uzp_dwh_company_holding_metric` |

Два источника указывают последовательно (`clckstrm_sbolpro_dim_event_type`); больше двух —
оставляют основной или опускают вовсе.

Если одна и та же сущность грузится и через СПОД, и через функцию, таблице с СПОД-загрузкой
добавляют постфикс `_manual` (`uzp_dwh_potential_client_manual`).

### Бизнес-сущность состоит из нескольких слов

После токена типа сущности идёт бизнес-сущность целиком — сколько бы слов в ней ни было.
«Лишних» токенов в именах ниже нет:

| Объект | Тип сущности | Бизнес-сущность |
| --- | --- | --- |
| `uzp_data_payroll_m` | `data` | `payroll_m` — ЗП-ведомости в месячном разрезе |
| `uzp_dwh_fact_outflow` | `dwh` | `fact_outflow` |
| `uzp_dwh_day_outflow` | `dwh` | `day_outflow` |
| `uzp_data_mzp_szp_pipeline_potential` | `data` | `mzp_szp_pipeline_potential` |
| `uzp_dwh_key_clients_scoring` | `dwh` | `key_clients_scoring` |

Разбор любого имени: начальные токены — направление и проект, затем тип сущности
(`dim` / `data` / `dwh` / `set` / `map`, перед ним возможен токен источника),
всё остальное — бизнес-сущность.

## Типы сущностей

| Тип | Что это | Описание объекта начинается со слов | Примеры |
| --- | --- | --- | --- |
| `dim` | список значений одной сущности | Справочник | `uzp_dim_gosb`, `uzp_dim_enrollment_type`, `uzp_dim_mkk_ca_base` |
| `data` | детальные данные, в том числе исторические | Детальные данные | `uzp_data_payroll_m`, `uzp_data_emp_epk_assignment`, `uzp_data_epk_consolidation` |
| `dwh` | расчётные данные | Расчетные данные | `uzp_dwh_fact_outflow`, `uzp_dwh_metrics`, `uzp_dwh_sap_staff_emp` |
| `set` | настроечная таблица | Настроечная таблица | цех: `dsa_set_asfs_role_privileges` |
| `map` | связь двух разных сущностей | Маппинг | цех: `mass_pers_map_epk2host_id` |

`dim` — одна сущность и её атрибуты (наименование должности и её id). `map` — пара
«сущность → сущность»; в имени маппинга обе сущности разделяются цифрой `2`
(`sap_map_saphr2pulse`). Тип сущности определяют до формирования имени.

## Система-источник

- Источник указывается в описании объекта в скобках и должен быть зарегистрирован в Реестре АС ДКА.
- Супермаркет данных (СМД) источником не считается — указывается реплика, из которой пришли данные.
- Для сущностей, рассчитанных на Greenplum, систему-источник в описании не указывают.
- Источники из разных ДЗО — источник указывается как «(ДЗО)».
- Источник неизвестен (например, почта) при задаче через СПОД — указывают, от кого получены данные.

Токены источников, которые встречаются в наших данных: `sap` (SAP HR — штатная численность,
`uzp_dwh_sap_staff_emp`), `isu` (ИСУ — задачи на руководителей), `jupiter` (Юпитер — номера
договоров, `jupiter_data_agrmnt_num`), `pprb` (ППРБ — один из источников задач наряду с ИСУ и ЦА).
Полный перечень источников — Реестр АС ДКА.

## Префиксы и постфиксы объектов

| Признак | Как оформляется | Пример |
| --- | --- | --- |
| Внешняя таблица на чтение из системы-источника — наш источник внутри функции `_calc` / `_upd` / `_del` | префикс `etl_`, постфикс `_r` | `etl_isu_dim_struct_r` |
| Временная таблица | префикс `tmp_` | `tmp_kk_base` (требования — `target-tables.md`) |
| История | постфикс `_hist` | цех: `crm_data_complaint_retail_hist` |
| Загрузка через СПОД | постфикс `_manual` | `uzp_dwh_potential_client_manual` |

Стейджинг под расчёт — временная таблица `tmp_stg_<витрина>`, целевая таблица — витрина УЗП,
см. `target-tables.md`.

External-таблица повторяет структуру источника: названия полей обязательны, типы — аналогичные
либо максимально близкие. Имя строят как
`etl_<функция без суффиксов _calc/_upd/_del>_<схема источника>_<таблица источника>_r`;
схему и имя таблицы можно опустить или сократить, если в функции одна таблица
(`etl_risk_atm_data_metric_status_agg_saphcm_hrarpa03`).

## Поля

Формула: `[бизнес-сущность]_[вид атрибута]`. Имя столбца не совпадает с именем таблицы.

### Виды атрибутов — постфиксы

| Постфикс | Значение | Тип данных | Пример |
| --- | --- | --- | --- |
| `_id` | числовой идентификатор | int2/int4/int8 | `epk_id` |
| `_code` | символьный код | text/varchar | `gosb_code` |
| `_guid` | код фиксированного формата `XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX` | text/varchar | `request_guid` |
| `_name` | наименование | text/varchar | `company_name` |
| `_descr` | описание | text/varchar | `metric_descr` |
| `_qty` | количество, целое | int2/int4/int8 | `outflow_qty` |
| `_cnt` | количество, дробное | numeric/float | `pos_cnt` |
| `_num` | номер | int2/int4/int8 | `group_num` |
| `_val` | значение (не денежный показатель) | numeric/float | `level_value` |
| `_amt` | сумма, объём, остаток (денежный показатель) | numeric | `fot_outflow_amt` |
| `_perc` | процент, доля | numeric | `outflow_perc` |
| `_dt` | дата | date | `report_dt` |
| `_dttm` | дата и время | timestamp | `inserted_dttm` |
| `_tm` | время | text/varchar | `start_tm` |
| `_flag` | флаг (не bool) | int2/int4/int8 | `workday_flag` |
| `_lvl` | уровень | int2/int4/int8 | `metric_lvl` |
| `_type` | тип | text/varchar | `enrollment_type` |
| `_list` | список | массивы int | `struct_type_list` |
| `_json` | список в JSON | json/jsonb | `dpan_card_num_list` |

### Идентификаторы

Только три вида: `id` — числовой (описание начинается с «Идентификатор»), `code` — текстовый
не-guid (описание с «Код»), `guid` — текстовый 36-символьный (описание с «Код»).
Исключение из правила описания — табельный номер: `saphr_id` описывается как «Табельный номер…».

### Даты

Только постфиксы `_dt`, `_dttm`, `_tm`. В спеке витрины для поля-даты указывается его вид
(`date` / `start_of_month` / `end_of_month`). Колонку партиционирования в условиях не оборачивают
в функции, иначе ломается отсечение партиций.

### Признаки и флаги

| Когда | Как | Тип | Описание начинается с |
| --- | --- | --- | --- |
| Да / Нет / Неизвестно | `is_[глагол в 3-й форме]`, `has_[существительное]`, `can_[глагол]` | всегда `bool` | «Признак» |
| Вариантов больше | постфикс `_flag` | никогда не `bool` | «Флаг» |

Наши признаки: `is_fot_enrollment`, `is_portfolio_enrollment`, `is_key_client`,
`is_outflow_return_success`, `is_task_closed_success`, `is_parent`.

### Показатели

Базовый постфикс показателя — `_val`, кроме: деньги → `_amt` (с уточнением валюты:
`rub_amt`, `ccy_amt`); целочисленный подсчёт → `_qty`; дробный подсчёт → `_cnt`;
отношение `val1/val2` → `_ratio_val`; разность `val1-val2` → `_diff_amt`.

Наши: `plan_amt` / `fact_amt`, `fot_y_1_diff_amt`, `fl_y_1_diff_qty`, `zp_fl_perc`.
В `uzp_dwh_metrics` доля выполнения лежит как `execution_percent`; новое поле доли —
`execution_perc`.

### Префиксы и порядок токенов

| Уровень | Токены | Куда ставится | Пример из наших витрин |
| --- | --- | --- | --- |
| 1-й | `new_`, `pre_`, `obsolete_`, `prev_`, `hash_`, `act_`, `is_`, `has_` | в самое начало | `prev_m_overflow_qty`, `new_fl_cnt` |
| 2-й — период | `y` год, `q` квартал, `m` месяц, `w` неделя, `d` день | в начало, если нет префикса 1-го уровня | `m_avg_salary_amt` |
| 3-й | `total`, `max`, `min`, `avg`, `norm`, `plan`, `fact` | в начало, если нет префиксов 1-го и 2-го уровней | `total_potential_qty`, `fact_payee_qty` |

Префикс периода и уровень значимости ставятся слева направо: `prev_m_avg_salary_amt`
(префикс 1-го уровня + период + 3-й уровень). Порядковый номер токена пишется раздельно
через `_`: `extended_dim_1` … `extended_dim_10`, `manager_lvl_1_saphr_id`.

Если в имени поля несколько видов атрибутов, отталкивайся от первого слова описания:
«Идентификатор уровня» → `lvl_id`, «Наименование группы идентификаторов» → `group_id_name`.

Глаголы в именах полей не склоняются (`task_create_dt`, `plan_close_task_dttm`), кроме
`inserted`, `updated`, `modified` и полей-признаков.

### Типы данных

Берётся минимально возможный тип: `int2` вместо `int8`, если значение влезает. Суммы —
`numeric(p, s)`, даты — `date`, моменты — `timestamp`, признак — `bool`.

## Описания объектов и полей

Описание объекта:

- начинается с типа сущности по-русски: «Справочник…», «Детальные данные…», «Расчетные данные…»,
  «Настроечная таблица…», «Маппинг…»;
- не начинается со слов «Таблица», «Витрина»; с заглавной буквы; без орфографических ошибок;
- отражает содержимое и принадлежность бизнес-процессу;
- система-источник в скобках — для загружаемых объектов; для рассчитанных на Greenplum — без неё;
- проект и бизнес-направление в текст описания не пишут (они в имени).

Примеры под наши витрины: «Расчетные данные фактических оттоков УЗП по ИНН и ГОСБ»,
«Справочник типов зачислений ЗП-ведомостей», «Детальные данные ЗП-ведомостей за месяц (SAP HR)».

Описание поля:

- не короче 5 символов;
- метод расчёта, расшифровка значений, формат — в скобках: «Тип процесса (Run - 1 / ReRun - 2)»,
  «Месяц и год отчётной даты (формат ГГГГ-ММ)»; исключение — период расчёта, он без скобок:
  «ФОТ за месяц T-1»;
- верхний регистр только для аббревиатур: «УРФ КОД» алгоритм прочитает как аббревиатуру и возьмёт
  в имя `kod`.

Текст описания объектов и полей вносится в DDL через `COMMENT ON` — требования к целевым
таблицам в `target-tables.md`.
