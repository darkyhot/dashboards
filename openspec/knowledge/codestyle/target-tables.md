# Целевые таблицы, временные таблицы и ETL-функции

Действует на боевой код: plpgsql-функции загрузки и расчёта, целевые витрины, стейджинги.
Оформление SQL (регистр, отступы, алиасы, комментарии) — в `sql-style.md`, имена объектов
и полей — в `naming.md`.

## Схемы департамента

| Схема | Назначение |
| --- | --- |
| `s_grnplm_ld_salesntwrk_pcap_sn_uzp` | прод: витрины УЗП; только чтение — источник данных |
| `s_grnplm_ld_salesntwrk_pcap_sn_t_uzp` | лабораторная (тестовая) область УЗП: здесь создают и заполняют витрины; отсюда вызывают системные функции (`sys_*`) и функции-помощники (`last_day`, `try_cast`) |

Схему в вызовах системных функций и функций-помощников указывают явно.

## Требования к целевой таблице

- Дистрибуция не по полям типов `date` и `timestamp`.
- `distributed randomly` не применяют при объёме меньше 10 млн строк.
- Партиций и субпартиций — не больше 1000; пустые партиции контролируют; default-партиций
  избегают.
- Индексы стараются не использовать.
- Описание обязательно: `comment on table` на объект и `comment on column` на каждый атрибут.
  Формулировки — по правилам `naming.md`, раздел «Описания объектов и полей».
  Для `etl_`-таблиц достаточно описания таблицы, поля — желательно.
- Storage-параметры целевой витрины (`appendonly`, `compresstype`, ключи дистрибуции,
  партиционирование) отражаются в спеке витрины (раздел о хранении).

## Временные таблицы

- Имя с префиксом `tmp_`.
- Только `create table` c последующим `insert`; `create table as select` в боевом коде запрещена.
- Сжатие не используют: для appendonly/appendoptimized таблиц явно указывают
  `compresstype=none`.
- После заполнения — `analyze` таблицы. Перед созданием — `drop table if exists`.
- Для `truncate` и сбора статистики на постоянных таблицах — только системные функции
  `sys_table_truncate` и `sys_table_analyze`; на временных таблицах они не нужны.
  Функции работают только с таблицами своей схемы `s_grnplm_ld_salesntwrk_pcap_sn_t_uzp`
  и дописывают её к имени сами. Имя передают без схемы:
  `s_grnplm_ld_salesntwrk_pcap_sn_t_uzp.sys_table_analyze(tbl := '<витрина>')`.
  Имя со схемой даёт ошибку `cross-database references are not implemented`.
- Стейджинг под целевую витрину называют `tmp_stg_<целевая витрина>`
  (`tmp_stg_uzp_dwh_key_clients_scoring`).
- Если временную таблицу планируют использовать несколько процессов — согласуют с владельцем
  схем (функционал общих временных таблиц заводится в схеме проекта).

## Порядок обновления целевой таблицы

1. Подготовка стейджинга или временной таблицы с данными, готовыми к вставке.
   Стейджинг можно не делать, когда источник читается как есть: `etl_`-таблица или витрина
   схемы `_data` / `_espd` выбираются без преобразований, фильтрации и join — типичный случай
   небольшой справочник.
2. Проверки подготовленных данных (при необходимости).
3. Удаление старой версии данных:
   - функция обновляет 20% и более записей — стейджинг содержит таблицу целиком, целевую
     таблицу на этом шаге транкейтят;
   - обновляется меньше 20% — удаляют только подлежащие замене записи.
4. Вставка новой версии данных из стейджинга.
5. Сбор статистики.

Такой же порядок — при маркировке данных через `update`. Сам `update` используют только
когда обновляется небольшое количество записей.

## Управляющая и вспомогательные функции

Имя функции строится от объекта, который она обновляет: `<имя объекта>_<глагол>`
(`uzp_dwh_key_clients_scoring_calc`). Если функция один к одному обновляет одну таблицу,
поток и функция называются одинаково.

| Глагол | Значение | Глагол | Значение |
| --- | --- | --- | --- |
| `load` | загрузка | `markup` | разметка |
| `calc` | расчёт | `ins` | вставка |
| `upd` | обновление | `del` | удаление |
| `mrg` | вставка-обновление-удаление | `get` | получение информации |
| `prepare` | предварительная подготовка | `format` | форматирование |

- Управляющая функция (её вызывает поток информатики) принимает ровно три параметра
  и в таком порядке: `p_etl_load_id int8`, `p_start_dttm timestamp`, `p_end_dttm timestamp`.
  Период формируется автоматически при создании потока; если период не требуется, в параметры
  приходят текущие дата и время.
- Вспомогательная функция (вызывается из других функций) обязана принимать `p_etl_load_id`
  — его передают из управляющей функции. Остальные параметры — на усмотрение разработчика.
- Параметры — с префиксом `p_`, переменные — с префиксом `v_` (`v_deleted_qty`).
- Сразу после `$$` — многострочный комментарий с разделами `Описание`, `Параметры`, `Изменения`
  (дата, автор, номер задачи в формате `SNDLAKE-****` / `SLSNTWRKDE-****`).
- Функция обязательна имеет `comment on function`.

Скелет функции с этими шагами — `templates/etl_function.sql`.

## Статусы процесса

Статус меняют процедурой `sys_data_etl_state_update(p_etl_load_id, p_state_id)`.

| Код | Смысл |
| --- | --- |
| `-1` | ошибка в процессе |
| `1` | начало процесса |
| `96` | процесс отработал частично |
| `97` | не пройдены проверки ККД |
| `98` | нет данных для расчёта или загрузки |
| `99` | процесс успешно завершён |

## Логирование

Перед каждым действием — запись в лог `sys_data_etl_log_write`; есть две перегрузки:
`(p_etl_load_id, p_log_message, p_error_code)` и
`(p_etl_load_id, p_function_name, p_log_message, p_error_code)`; `p_error_code` заполняют
обязательно, когда пишут сообщение об ошибке, иначе `null`.

- Формат сообщения: `номер шага - текст`, например `10 - проверка наличия данных`.
- Номер шага — число от 02 до 99, всегда двумя цифрами (двойка — `02`).
- Успешное завершение — шаг `99`, отсутствие данных для расчёта — `98`.
- В цикле каждая итерация пишет `[номер шага].[номер итерации]`:
  `10.01 – обработка данных за 2021-06-30`.
- Ошибка обязательно сохраняется в лог.
- Если текст сообщения полностью повторяет комментарий к действию, комментарий не пишут.

## Проверки ККД

Проверка входных данных — отдельный шаг функции с собственным номером. Типовые проверки:
наличие данных в источнике за расчётную дату и отсутствие повторного расчёта за эту дату
(чтобы перезапуск не накладывал дубли). Если условие не выполнено — в лог пишут `98 - ...`
или `97 - ...` с указанием витрины, ожидаемой и фактической даты, затем ставят соответствующий
статус и делают `return`.

## Транзакции и обработка ошибок

Внутри функций Greenplum управлять транзакциями нельзя. Порядок исполнения организуют
вложенными и последовательными блоками `begin – exception – end`: при ошибке в блоке откатываются
все его действия, включая вложенные блоки. `when others then` гасит исключения блока — команды
до `exception` откачены, команды после неё выполнены. В блоке ошибки — запись в лог через
`get stacked diagnostics` (sqlstate, сообщение, деталь, hint, контекст, колонка, ограничение,
тип, таблица, схема), статус `-1` и `return`.

Количество затронутых строк получают через `get diagnostics v_row_count = row_count`.

## Системные функции платформы

| Функция | Параметры | Назначение |
| --- | --- | --- |
| `sys_data_etl_state_update` | `p_etl_load_id int8`, `p_state_id int2` | изменить статус экземпляра процесса |
| `sys_data_etl_log_write` | `p_etl_load_id int8`, `p_log_message text`, `p_error_code text` | запись в лог |
| `sys_data_etl_log_write` | `p_etl_load_id int8`, `p_function_name text`, `p_log_message text`, `p_error_code text` | запись в лог с именем функции |
| `sys_table_truncate` | `tbl text` — имя без схемы | truncate постоянной таблицы схемы `t_uzp` |
| `sys_table_analyze` | `tbl text` — имя без схемы | сбор статистики по постоянной таблице схемы `t_uzp` |

Функции работы с датами и `try_cast` — в `sql-style.md`, раздел «Даты и функции-помощники».
