# 2. Постановка задачи

## 2.1. Описание решаемой бизнес-задачи

Сотрудникам УЗП ставятся задачи по клиентам. Основание задачи — триггер: событие или состояние
клиента, например клиент впервые перечислил ЗП, у клиента отток портфеля, сотрудники клиента
подают заявления на перечисление ЗП через ВСП.

Витрина `uzp_dwh_task_trigger` хранит сработавшие триггеры по паре ИНН + ГОСБ за месяц или за
неделю. Параметры триггера — в JSON. По витрине строятся задачи.

Две функции расчёта:
- ежемесячная — 15 триггеров за месяц;
- еженедельная — 2 триггера по заявлениям ВСП за неделю Пн–Вс.

### 6.1.2. Описание задачи

**Что разработать**

Вывести витрину `uzp_dwh_task_trigger` для формирования задач сотрудникам УЗП.
Реализовать ежемесячную и еженедельную функции расчёта.
Одна строка результата — один сработавший триггер по паре ИНН + ГОСБ за период.
Параметры триггера сохранять в `attributes_json`. Строки записывать только при наличии ИНН и ГОСБ.

| # | **Что делаем** | **Логика расчета** | **Период расчета** |
| --- | --- | --- | --- |
| 1 | Создать витрину `uzp_dwh_task_trigger` | Хранить сработавшие триггеры и их параметры. Атрибутный состав — в 5.1 | Месяц / неделя |
| 2 | Реализовать `uzp_dwh_task_trigger_month_calc` | Рассчитывать 15 ежемесячных триггеров по показателям клиента, заявлениям, договорам и задачам | Месяц `p_end_dttm` |
| 3 | Реализовать `uzp_dwh_task_trigger_week_calc` | Рассчитывать 2 еженедельных триггера по заявлениям без зачислений, с учётом наличия договора | Неделя `p_end_dttm` |

**Ежемесячная функция `uzp_dwh_task_trigger_month_calc`**

Рассчитать перечисленные ниже триггеры. Период результата — полный месяц `p_end_dttm`:
`start_dt` — первое число, `end_dt` — последнее.
T — последний день этого месяца, T-k — последний день месяца на k раньше.
Портфель — количество получателей ЗП на карту банка. Потенциал — численность сотрудников за вычетом портфеля.

В триггерах по заявлениям считать отдельно бумажные и электронные заявления, включая число заявлений с ЗП-зачислением.
Зачисление учитывать по человеку с даты заявления по текущую дату, от любой организации и без порога суммы.
Действующий договор определять по ИНН независимо от ГОСБ: дата окончания отсутствует или не раньше текущей даты.

| # | **Название триггера** | **Тип** | **Условие срабатывания** | **Период расчета** |
| --- | --- | --- | --- | --- |
| 1 | ЕПП флаг | Вспомогательный | В навигаторе за отчётную дату и дату методологии T у пары есть только выплаты по ЕПП | T |
| 2 | Ср чек ниже среднего | Вспомогательный | Средняя зарплата клиента ≤ 0,8 × средней по ГОСБ и отрасли. Средняя — сумма ФОТ / сумма получателей за месяцы с ненулевым числом получателей. Пары без отрасли исключить | T-5…T |
| 3 | Отрицательный потенциал | Основной | Количество НП превышает потенциал: `np_cnt > emp_potential_qty` | T |
| 4 | Кп первое зачисление | Основной | ФОТ за T положительный, за каждый из предыдущих 12 месяцев — 0 | T-12…T |
| 5 | Сезонный тип деятельности | Основной | Рост портфеля из месяца T+1 в T+2 год назад и два года назад составляет не менее 10% в каждом году. Нулевая база — роста нет | T-23…T-10 |
| 6 | Высокая текучка | Основной | НФЛ > 0, НП < 20% от НФЛ, портфель за T снизился относительно T-1 | T-1…T |
| 7 | Есть договор нет зачисления | Вспомогательный | У пары есть действующий договор ИНН, начавшийся не позже текущей даты минус 6 месяцев. ФОТ равен 0 в каждом месяце T-5…T | T-5…T |
| 8 | Контактная политика 4 месяца | Основной | Нет закрытых задач МЗП из источников кроме ИСУ и ПРБР с датой закрытия от первого числа T-3. Верхняя граница даты отсутствует | с 1-го числа T-3 |
| 9 | Бумажные заявления из ВСП или МП СБОЛ за прошлый месяц | Вспомогательный | У пары есть бумажные заявления за расчётный месяц | T |
| 10 | Электронные заявления из ВСП или МП СБОЛ за прошлый месяц | Вспомогательный | У пары есть электронные заявления за расчётный месяц | T |
| 11 | Бумажные заявления из ВСП или МП СБОЛ за последние три месяца | Вспомогательный | У пары есть бумажные заявления за последние 3 месяца | T-2…T |
| 12 | Электронные заявления из ВСП или МП СБОЛ за последние три месяца | Вспомогательный | У пары есть электронные заявления за последние 3 месяца | T-2…T |
| 13 | По клиенту был отток в прошлом месяце, численность | Основной | По данным оттока `outflow_qty ≥ 3` и `fact_payee_qty < prev_m_fl_val` | T |
| 14 | По клиенту был отток в последние три месяца | Основной | Условие оттока за месяц выполнено в каждом из месяцев T-2, T-1 и T | T-2…T |
| 15 | Доля по клиенту больше 90% | Вспомогательный | Доля получателей ЗП на карту банка среди сотрудников клиента `zp_fl_perc > 0,9` | T |

**Еженедельная функция `uzp_dwh_task_trigger_week_calc`**

Рассчитать перечисленные ниже триггеры по бумажным и электронным заявлениям вместе.
Период результата — неделя `p_end_dttm`: `start_dt` — понедельник, `end_dt` — воскресенье.
В расчёт включать заявления с датой подачи внутри этой недели.

Для каждой пары определить наличие действующего договора ИНН и количество заявлений без ЗП-зачисления.
Договор учитывать независимо от ГОСБ: дата окончания отсутствует или не раньше текущей даты.
Зачисление учитывать по человеку с даты заявления по текущую дату, от любой организации и без порога суммы.
Если все заявления пары имеют зачисления, триггер не срабатывает.

| # | **Название триггера** | **Тип** | **Условие срабатывания** | **Период расчета** |
| --- | --- | --- | --- | --- |
| 1 | Заявление из ВСП без договора и зачислений | Основной | У ИНН нет действующего договора, у пары есть хотя бы одно заявление без зачисления | Неделя Пн–Вс |
| 2 | Заявление из ВСП с договором без зачислений | Основной | У ИНН есть действующий договор, у пары есть хотя бы одно заявление без зачисления | Неделя Пн–Вс |

## 6.2. План обновления данных

| Периодичность запуска обновления |  |
| --- | --- |
| **Тип обновления** | Инкрементальное: перерасчет одного периода |
| **Логика обновления** | Функция удаляет из витрины строки своих триггеров (по `trigger_name`) за `start_dt` / `end_dt` расчета и вставляет новые. Строки другой функции и других периодов не меняются. Повторный запуск за тот же период заменяет строки, дублей нет |
| **Последовательность запуска (если есть зависимости)** | После загрузки источников за период. Ежемесячная: `uzp_dwh_company_holding_metric`, навигатор, `uzp_dwh_fact_outflow`, `vsp_data_salary_detail_report` за месяц T, `mis_data_payroll_d` за месяц T. Еженедельная: `vsp_data_salary_detail_report` за неделю, `mis_data_payroll_d` с начала недели. Функции друг от друга не зависят |
| **Контроль обновления** | Данные не обновляются, если у источника нет данных за период или не пройдена обязательная проверка ККД (6.3): статус 98, в витрине остаются старые данные |

## 6.3. Контроль качества данных

Все проверки добавлены сразу в код прототипа. Не прошла проверка — запись в лог `98 - ...`,
статус 98, функция завершается, витрина не меняется.

| # | **Проверка** | **Шаг лога** |
| --- | --- | --- |
| 1 | У каждого источника есть данные за период. Ежемесячная: `uzp_dwh_company_holding_metric` за T; навигатор за `report_dt` = T и `version_plan_dt` = T; заявления за `report_m_dt` = T; `uzp_dwh_fact_outflow` за T; `mis_data_payroll_d` за месяц T; остальные источники не пусты. Еженедельная: заявления за неделю; `mis_data_payroll_d` с `start_dt`; справочники и договоры не пусты. В лог — источник, ожидаемая и фактическая последняя дата | 02 |
| 2 | После чтения каждого источника во временную таблицу — число строк не 0 | 10.NN |
| 3 | Каждое деление — через `case` с проверкой знаменателя на 0. Знаменатель 0 — показатель null, условие триггера не выполнено | 20.NN |
| 4 | Перед `delete` витрины — в стейджинге не 0 строк | 21 |
| 5 | Перед `delete` витрины — в стейджинге нет дублей по ключу `inn`, `gosb_id`, `trigger_name` (период в запуске один) | 21 |
| 6 | Ошибка выполнения — запись в лог с `sqlstate`, статус -1 | каждый блок |

## 6.4. Верификация

1. Ключ витрины уникален:
   `select inn, gosb_id, trigger_name, start_dt, end_dt from uzp_dwh_task_trigger group by 1, 2, 3, 4, 5 having count(*) > 1` — пусто.
2. Сверка с источником: строк 'Отрицательный потенциал' за T столько же, сколько пар `uzp_dwh_company_holding_metric` за T с `level_name = 'gosb'`, `org_type = 'inn'`, `np_cnt > emp_potential_qty`.
3. У всех строк одного запуска одно `modified_dttm`.
4. У ежемесячных строк `start_dt` — 1-е число, `end_dt` — последний день месяца; у еженедельных — понедельник и воскресенье.
5. Повторный запуск за тот же период: число строк не меняется, дублей нет.
6. Запуск еженедельной функции не меняет строки ежемесячных триггеров за тот же месяц.
7. Ключи `attributes_json` у каждого триггера совпадают с составом JSON в прототипе соответствующей функции (6.1.3).
8. Нет данных источника за период — статус 98, витрина не изменилась.
