# 2. Постановка задачи

## 2.1. Описание решаемой бизнес-задачи

Сотрудникам УЗП ставятся задачи по клиентам. Основание задачи — триггер: событие или состояние
клиента, например клиент впервые перечислил ЗП, у клиента отток портфеля, сотрудники клиента
подают заявления на перечисление ЗП через ВСП.

Витрина `uzp_dwh_task_trigger` хранит сработавшие триггеры по паре ИНН + ГОСБ за месяц или за
неделю. Параметры триггера — в JSON. По витрине строятся задачи.

Две функции расчёта:
- ежемесячная — 15 триггеров за месяц;
- еженедельная — 2 триггера по заявлениям ВСП за неделю Пн–Вс.

### 6.1.2. Описание задачи

Обозначения: T — последний день расчетного месяца, T-k — последний день месяца на k раньше.
hm — `uzp_dwh_company_holding_metric` с `level_name` = 'gosb', `org_type` = 'inn': пара —
`org_id` (ИНН) + `level_id` (ГОСБ). Портфель — получатели ЗП на карту банка (`current_fl_qty`),
численность — все сотрудники (`total_emp_qty`), потенциал — их разность (`emp_potential_qty`).
Во всех JSON ежемесячных триггеров есть ключ `month` = T.

## 6.2. План обновления данных

| Периодичность запуска обновления |  |
| --- | --- |
| **Тип обновления** | Инкрементальное: перерасчет одного периода |
| **Логика обновления** | Функция удаляет из витрины строки своих триггеров (по `trigger_name`) за `start_dt` / `end_dt` расчета и вставляет новые. Строки другой функции и других периодов не меняются. Повторный запуск за тот же период заменяет строки, дублей нет |
| **Последовательность запуска (если есть зависимости)** | После загрузки источников за период. Ежемесячная: `uzp_dwh_company_holding_metric`, навигатор, `uzp_dwh_fact_outflow`, `vsp_data_salary_detail_report` за месяц T, `mis_data_payroll_d` за месяц T. Еженедельная: `vsp_data_salary_detail_report` за неделю, `mis_data_payroll_d` с начала недели. Функции друг от друга не зависят |
| **Контроль обновления** | Данные не обновляются, если у источника нет данных за период или не пройдена обязательная проверка ККД (6.3): статус 98, в витрине остаются старые данные |

## 6.3. Контроль качества данных

Все проверки добавлены сразу в код прототипа. Не прошла проверка — запись в лог `98 - ...`,
статус 98, функция завершается, витрина не меняется.

| # | **Проверка** | **Шаг лога** |
| --- | --- | --- |
| 1 | У каждого источника есть данные за период. Ежемесячная: hm за T; навигатор за `report_dt` = T и `version_plan_dt` = T; заявления за `report_m_dt` = T; `uzp_dwh_fact_outflow` за T; `mis_data_payroll_d` за месяц T; остальные источники не пусты. Еженедельная: заявления за неделю; `mis_data_payroll_d` с `start_dt`; справочники и договоры не пусты. В лог — источник, ожидаемая и фактическая последняя дата | 02 |
| 2 | После чтения каждого источника во временную таблицу — число строк не 0 | 10.NN |
| 3 | Каждое деление — через `case` с проверкой знаменателя на 0. Знаменатель 0 — показатель null, условие триггера не выполнено | 20.NN |
| 4 | Перед `delete` витрины — в стейджинге не 0 строк | 21 |
| 5 | Перед `delete` витрины — в стейджинге нет дублей по ключу `inn`, `gosb_id`, `trigger_name` (период в запуске один) | 21 |
| 6 | Ошибка выполнения — запись в лог с `sqlstate`, статус -1 | каждый блок |

## 6.4. Верификация

1. Ключ витрины уникален:
   `select inn, gosb_id, trigger_name, start_dt, end_dt from uzp_dwh_task_trigger group by 1, 2, 3, 4, 5 having count(*) > 1` — пусто.
2. Сверка с источником: строк 'Отрицательный потенциал' за T столько же, сколько пар hm за T с `np_cnt > emp_potential_qty`.
3. У всех строк одного запуска одно `modified_dttm`.
4. У ежемесячных строк `start_dt` — 1-е число, `end_dt` — последний день месяца; у еженедельных — понедельник и воскресенье.
5. Повторный запуск за тот же период: число строк не меняется, дублей нет.
6. Запуск еженедельной функции не меняет строки ежемесячных триггеров за тот же месяц.
7. Ключи `attributes_json` у каждого триггера совпадают с 6.1.2.
8. Нет данных источника за период — статус 98, витрина не изменилась.
